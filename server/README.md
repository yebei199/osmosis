# server

axum 后端。两个职责:与客户端共享 `contract`(线上格式的一致性由编译器保证),
以及把 bang-dream 的 gRPC 翻译成 HTTP/JSON。

它同时是**自家数据的家**:账号、本地歌单、播放事件落在 Postgres。
平台那边的东西真相在上游 —— 判据是每份数据的真相在谁手里(见 `docs/adr/0016`)。
平台曲目在这边留一份**缓存**,那不改变真相在谁手里(见 `docs/adr/0018`)。

## 模块

| 位置             | 内容                                                                     |
|------------------|--------------------------------------------------------------------------|
| `src/main.rs`    | 进程装配:状态、路由表、监听。路由留在这里,它们是装配方式不是可复用的库   |
| `src/gate/`      | 请求进门那一道:token 换账号的提取器、限流                                |
| `src/store/`     | 自家数据:连接池与迁移、账号、本地歌单、播放事件、平台曲目缓存            |
| `src/syncplay/`  | 同播与遥控的信令。与音乐那半毫无关系,state 也不共用                      |
| `src/routes/`    | HTTP 处理函数,按资源分:`catalog/` 平台那边的、`library/` 我的库、其余在根 |
| `src/bangdream.rs` | 唯一认识 gRPC 的地方;上游领域模型到 `contract` 的翻译                  |
| `src/error.rs`   | `AppError` 与两条映射:自家的失败、上游 gRPC 的失败                       |

每个子目录的 `README.md` 写了它负责什么、不负责什么。

## 下载要一个 ffmpeg

`/download/{id}` 承诺交出来的**永远是 mp3**。源已经是 mp3 就原样透传,别的格式
(无损档给的是 flac)现起一个 `ffmpeg` 转。转码放这一侧而不是客户端:LAME 是 C
依赖,安卓要交叉编译进包、wasm 端根本编不了,而手机上转一首 flac 是几十秒的满载
CPU。代价是这个进程多了一个**外部可执行文件**依赖 —— 镜像里由
`server/Dockerfile` COPY 进来,本地开发由 `slint.nix` 提供。

失败只在第一个字节之前说得出口:`200` 发出去之后 HTTP 没有回头改状态码的余地,
之后的失败只能表现为截断的响应。所以落盘那一侧要写进临时态、收全才提交。

## 鉴权写在签名里

`Account` 是**提取器**不是中间件。中间件的话,「这条路由要不要鉴权」记在路由装配处,
与 handler 隔着一段距离,加新路由时最容易漏。做成参数之后,handler 的参数表上有
`Account` 就是要,没有就是不要。

同理,每次上游调用都要 `bangdream::as_user(&account, …)` 包一层 —— 上游按这个
metadata 分片保存平台凭据,不带就一律 `INVALID_ARGUMENT`。忘了包的现象是 `account`
参数没被用到,而 clippy 门禁是 `-D warnings`,于是它是**编译期错误**。

## 事件流只增不改

播放事件起播即追加一条,不记"听了多久":补记要靠客户端在退出或切歌时再发一次,
而崩溃与断网时那一条就丢了。「最近播放」「最常听」都是**查询时**的聚合,
没有统计表也没有定时任务 —— 口径想改就改,因为原始事件都在。

去重同理只发生在查询时:一次单曲循环在列表里只占一行,但事件流里那五条一条不少。

排序用主键不用时间戳:主键是严格递增的插入顺序,不依赖时钟,而同一个事务里
插入的几条 `now()` 完全相同。

## 数据库

- 连不上就不启动。到 bang-dream 的连接是惰性的(它没起来只影响用到它的请求),
  但没有数据库连登录都办不成,带着一个必然 500 的服务活着只会更难查。
- 迁移在启动时跑,`migrations/` 目录编进二进制。少一个能忘的部署步骤。
- **不用 `sqlx::query!` 宏**:它要在编译期连库校验 SQL,会让 `cargo build` 依赖一个
  跑着的 Postgres。一律用运行时的 `query_as`,SQL 由测试盖住。
- 起库:`just pg`。测试直接对着它跑。`tests/` 下的每条在自己的事务里回滚,因此可以
  并行、也不留数据。路由那几条(`src/routes/*/tests.rs`)例外 —— handler 自己从池里
  取连接,塞不进测试的事务;它们改用固定的账号名与曲目 id 前缀,开跑先清上一轮的残留,
  见 `src/routes/testing.rs`。
- 路由测试的上游由**进程内的假 gRPC 服务**扮演(同一个文件)。handler 拿的是
  `CatalogServiceClient<Channel>` 这种具体类型,中间没有可替换的接口,所以 `build.rs`
  连 server 桩一并生成 —— 生产代码一个都不实现。

## 缓存不是镜像

`cache.rs` 里那两张表存的是平台的东西,但它们不是第二份真相。三条规矩把它钉在
缓存这一侧:写永远直发平台、冲突时平台赢、整张删掉只是慢一次而不丢东西。

因此这个模块只有「补齐、整体覆盖、读回来」这几个动作 —— 没有「往缓存里加一首」,
那是写,而写不在这里发生。判定问题:**删了会丢数据吗**?会,那它已经不是缓存了
(见 `docs/adr/0018`)。

歌单类的路由**不切页**:歌单是一整批,973 首里只给 50 首的话,剩下的 923 首没有
任何入口。向平台要的只有**缺详情**的那些 —— 成员关系点一次红心就变一次,而详情
几乎不变且跨歌单共用,每次全量重取的话这个缓存等于没有。

平台歌单(含红心)**先回库、后台回源**(#124,`catalog_cache::store_first`):
库里那份 24 小时内就直接答它,距上次回源满 30 秒才在后台再回源一次,下一次打开
看到结果。在这边点的心当场作废红心那份。「多新」只记在进程内存里 —— 重启后
每个歌单第一次打开当场回源,与整张删掉缓存同理,只是慢一次。

本地歌单只借详情那一半:它的成员关系真相在 `local_playlist_tracks`。写进
`platform_playlist_tracks` 的话,本地歌单的整数 id 会和平台歌单的字符串 id 撞在
同一个 TEXT 列上。

## 归属检查写进 WHERE

本地歌单的每个函数都收 `account_id` 并把它写进查询条件,而不是先查一次再判断。
分成两步就总有一天会漏掉第一步;写进 WHERE 之后,漏了的现象是查不到东西。

不是自己的歌单一律按**不存在**处理,不回 403 —— 那等于确认了这个 id 存在。
