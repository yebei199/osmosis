# bang-dream 只搬运平台字段,语义判断交给 axum 后端

日期:2026-08-09。状态:已采纳。收缩 bang-dream 防腐层的边界。

## 背景

bang-dream 一直按防腐层定位:把平台的私有概念挡在外面,只给调用方一套平台无关
的形状。`isLikedPlaylist` 是这个定位最完整的一次表达 —— 它按 `specialType == 5`
认出红心歌单,并把它从用户歌单列表里整个剔掉。剔掉的理由写在注释里,而且是对的:
红心在这套 API 里已经有专门的一道门,两处都报的话,调用方的列表里会并排站着
两个同样的歌单,而它们连 id 都不一样,去重的活没人干得对。

那段注释的最后一句是:「代价是调用方从此拿不到红心歌单的 id,目前没有人需要它。」

现在有人需要了。`docs/adr/0021` 要按加入时间排序,而加入时间只在歌单详情的
`trackIds[].at` 里 —— 要取那份详情,就得先有红心歌单的 id。同一处解析还顺手
把 `trackIds` 元素除 `id` 之外的字段全部丢掉了,`at` 一直就在那个 map 里,
只是没人读。

一个防腐层挡住的不再只是平台的脏东西,还有调用方真正需要的数据。那就该重新
划边界,而不是在它上面开洞。

## 决策

bang-dream 对平台响应**只做搬运**:

- 透传 `special_type` 与 `at`,不再从用户歌单列表里剔掉红心歌单。
- 「哪个歌单是红心」「按什么排」由 osmosis 的 axum 后端决定。

防腐层的边界收缩到**数据形状**:字段命名、类型、分页语义、请求顺序与响应顺序
的对齐,这些仍然由 bang-dream 抹平(`TracksByIDs` 按请求顺序重排返回结果那种活,
继续归它)。**语义判断**不再由它承担。

一句话的判据:bang-dream 可以决定一个字段**叫什么、是什么类型**,不再决定
它**意味着什么**。

## 备选方案

**用平台无关的 `is_liked` 布尔暴露。** 不选:那仍然是 bang-dream 替调用方做
判断,而判据(`specialType` 的取值表)只有平台自己知道。平台改了取值,bang-dream
跟着改,调用方却看不见自己依赖的到底是什么 —— 出错时现象是「红心歌单突然变成
一个普通歌单」,而没有任何一处代码提到过 5 这个数。

**新开一个 `GetLikedPlaylist` 方法。** 不选:方法名本身就是业务语义,与「只搬运」
直接相左。而且特殊歌单不止红心一种(年度歌单是 20),迟早要同样处理,那时又得
开一个方法,一个一个开下去防腐层就变成了业务层。

## 代价

- **网易云的私有枚举漏进 axum 后端**。`special_type == 5` 这个魔数从此住在
  Rust 侧。接第二个平台时,那里会长出平台分支 —— 而这正是 bang-dream 当初
  存在的理由之一。这是本次交易的价格,写在这里以便将来有人想把它买回去。
- **歌单列表里从此会出现红心歌单**,调用方必须自己排除它,否则界面上会并排
  站着两个「我喜欢的」。`docs/adr/0016` 担心的正是这个,现在这份责任转移到了
  axum 后端,必须有测试钉住,不能靠记性。
- 「bang-dream 是防腐层」这个说法从此要带限定:**它抹平形状,不判断语义**。
  只说前半句会让人以为平台概念不会出现在 Rust 侧,而现在会。
