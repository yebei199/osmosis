# 遥控器模式是名册上的第二种会话形态,不是同播的一个变种

日期:2026-09-19。状态:已采纳。与 `0008`(同播是 WebRTC 媒体 P2P)并列,不取代它。

## 背景

想要的能力:在手机上选一台**同账号已登录**的设备(可以是本机),之后照常搜歌、
点歌、切歌、拖进度,但出声全在被选中的那台上,进度条显示的是那台的真实进度。
首要场景是手机遥控 pc1。

它和同播正好相反。同播是主控出声、听众收流、控制单向归主控(`0008`);遥控器
模式是**遥控器不出声**、被控端自己拉直链自己播、控制权归遥控器。硬塞进同播的
主控/听众模型,会把 `0008`「控制单向归主控」那条推翻 —— 而那条不是实现细节,
它是「听众按任何播放键都视为退出收听」这条产品规则的根。

## 决策

**遥控器模式是同一账号名册上的第二种会话形态**,与同播共用信令连接与名册,
但状态、界面与规则各自独立。音频一个字节都不过网。

### 一、进度靠被控端上报,不靠遥控器推算

各设备网速不同,「点了播」到「真出声」之间的延迟不可知。遥控器推算出来的位置
必然与音箱里的声音对不上,而且不会有任何报错 —— 那是最难查的一类错。

被控端每秒上报一次 `{track, position_ms, state, queue, queue_index, volume, sent_at}`。
遥控器在两次上报之间按**本地**时钟插值,`buffering` 与 `paused` 时不插值(那一刻
进度并没有在走,照插会让进度条自己往前爬、再在下一次上报时跳回去)。连续三秒
收不到上报就标「状态已过期」、禁用控制,但**不自动切回本机** —— 切回去的话用户
一低头就发现歌从手机里放出来了,而他要的是让 pc1 放。

`sent_at` 是被控端自己的挂钟,**不用来对时**:两台设备的钟本来就不一样。它只
回答「这条比那条新吗」,挡住重连后旧连接上迟到的残余上报。过期与否由收信方按
自己的钟判。

拖进度沿用 `0019` 的异步加有界裁决,裁决由被控端回 —— 跳不跳得动,只有拿着那条
流的那端知道。

### 二、队列归被控端

遥控器发的是「播这份列表,从第 i 首开始」,整批过去。自动续播因此在被控端发生,
遥控器锁屏、断线、没电都不影响。遥控器只显示被控端回报的队列,不持有自己那一份。

### 三、控制权是服务端持有的单槽位,带代次

每账号一个槽:`ClaimControl` 写入并把旧遥控器踢成 `ControlRevoked`;`Command` 只
转发代次匹配的遥控器发来的;被控端 `ExitControlled` 清槽。服务端仍然**不解释**
`Command` 与 `State` 的内容,只做归属与转发 —— 与 `Signal{to, payload}` 同一模式。

`ClaimControl` 带一个可选的代次,把「主动接管」与「重连续上」分开:没有代次是
用户按下的那一次,顶掉任何人;带代次是重连时自动重发的那一次,槽位换人就只能
认输。不分的话,「旧遥控器自动重连**不**夺回」这条产品规则落不了地 —— 断线的
手机一恢复网络就会把接管者顶掉,而接管者那边什么都没做过。

两侧的下线规则**相反**,这是最容易写反的一处:被控端下线清槽并通知遥控器;
遥控器下线**不**解锁被控端,手机没电不能让 pc1 停。

### 四、快照向被控端要,服务端不缓存

遥控器取得控制权、换目标或重连之后各要一次 `SnapshotRequest`,被控端立刻回一条
完整上报。服务端不缓存状态:缓存了就要维护它的归属、版本与过期,而这三样每一样
都能单独把「显示的进度」弄错,收益只是省掉一次往返。

### 五、app-core 引入「输出设备」抽象

「输出设备 = 谁」**就是**遥控器模式的全部状态,不多一个模式开关。`Output::Local`
让现有路径一个字节都不变;`Output::Remote` 把播放动作换成命令、把播放状态换成
对方的上报。界面层只认这一个抽象,不为两种输出各画一套控制条。

落点是**回调入口**那六处(点歌、播放键、上下首、拖进度、音量),不是散在各自的
实现里 —— 那样总有一个会被漏掉,而漏掉的那个表现为「别的键都遥控,唯独这个还在
本机上放」。

## 后果

- 契约多出一组遥控消息与一个命令集。服务端读得懂外层的 `to`,读不懂 `cmd`。
- `ClientSignal` 与 `ServerSignal` 不再派生 `Eq`:音量是 0..1 的 `f32`。
- 被控端多一个锁定态:被遥控期间本机上的播放动作一概不生效,界面挂「正被 xx
  遥控」与一颗退出键。按了才恢复,同时撤销遥控器的控制权。
- 同一账号同时只有一台遥控器。想同时遥控两台设备,这套模型办不到 —— 那要把
  单槽位换成一张表,以及一套「这条命令是发给谁的」的界面,现在没有需求。
- 系统媒体控件(锁屏)这一轮不跟着遥控走:它读的仍是本机的播放状态。

## 被否决的做法

- **扩展同播让听众发控制**:推翻 `0008` 的「控制单向」,而那条是听众语义的根。
- **WebRTC DataChannel 传命令**:为每分钟几条几十字节的小消息多维护一套 ICE
  协商,而信令连接本来就在那儿、本来就是可靠有序的。
- **被控端暴露 HTTP 控制口**:pc1 在 NAT 后面,手机根本连不上。
