# 0019 跳转是异步的,但裁决有界等待

日期: 2026-08-02

状态: 已接受

## 背景

播放链路是 `Tee(buffered(normalize(decoder)))`。`buffered` 把解码搬到自己的线程,
隔着一条 mpsc 通道喂 `ChannelSource` —— 这一层的**全部理由**是不让声卡回调碰网络
(见 `docs/adr/0013` 与 `crates/audio/src/stream_source.rs` 的模块头)。

代价是 rodio 手里只剩通道的接收端,而通道不认识"第几秒"。进度条因此从一开始
就是死的:任何一次拖动都报 `Seeking is not supported by source:
Tee<Tee<ChannelSource>>`。

要让跳转生效,请求必须穿过通道交给解码线程执行。于是出现一个时序问题:
`Source::try_seek` 是 rodio 在**声卡回调里**调的(`periodic_access`,5ms 一次),
而解码线程执行一次跳转可能要好几秒 —— 跳到还没下到的位置要重开一个 range 请求。

## 决定

`ChannelSource::try_seek` 把请求送给解码线程,然后**有界地**等一个裁决
(`SEEK_VERDICT_WINDOW`,10ms):

- 裁决及时到:如实返回 `Ok`/`Err`。
- 等不到:乐观返回 `Ok`,结论随后留在 `SeekState` 上,界面每秒问一次。

请求带着一条**新通道**。缓冲里躺着最多 5 秒的旧采样,换通道让"丢到哪一个为止"
这个界碑变成通道本身,两条线程不必约定别的。

## 为什么有界,而不是两个极端

**一直等**会让混音器停摆整个取字节的时间。那正是 `buffered` 要躲开的事,
为了跳转把它放回来是自相矛盾。

**完全不等**(纯乐观)会让进度条说谎。rodio 的 `TrackPosition::try_seek` 只在
inner 返回 `Ok` 时才把 `offset_duration` 挪过去 —— 一个无条件的 `Ok` 正好骗过它。
真机日志里这么记着:

    位置 194.328s → 29.238s      # 进度条跳了
    WARN 跳转到 29.013s 失败      # 声音没跳

界面会说「这首跳不了」,而那个数字是错的,直到下一次跳转成功为止。一个报了错
还继续走的进度条,比一个跳不动的进度条更难判断到底发生了什么。

有界让两种失败落在各自该去的地方,而这是因为**跳不动的失败恰恰都是快失败**:
`ForwardOnly`、`AccurateSeekNotSupported` 这类根本不读网络,微秒级返回。慢的
只有"真在取字节",而那种情况位置先跳过去反而是对的 —— 它真的在往那儿去。

10ms 的两头:下界是快失败那条路只需两次线程唤醒,10ms 是它的十倍余量;上界是
本仓库量到的一次 cpal 回调预算 21ms,取一半,最坏赔上一块缓冲 —— 而那一刻本来
就在跳转,声音本来就断。

## 后果

- `try_seek` 返回 `Ok` 不等于跳成了。读这段代码的人必须知道这一点,否则会把
  `SeekState` 当成冗余而删掉。
- 结论走两条路中的**一条**,不是两条:裁决送得进去说明调用方还在等,它自己报;
  送不进去说明它超时走了,那才留在 `SeekState` 上。两条都走的话同一次失败会被
  说两遍 —— 一遍来自拖动那一下,一遍来自一秒后的轮询。
- 界面因此有两条报告路径,`crates/ui/src/music.rs` 的 `bind_seek` 与
  `push_seek_state` 各管一条。
- 听同播时没有解码线程,控制通道生下来就是断的,`try_seek` 如实报错。这不是
  额外的标志位,是同一套机制的自然结果。

## 相关

- `docs/adr/0013`:断流与放完了的区分,`buffered` 的另一半理由。
- 根因另有一条:rodio 的 `Decoder::new` 默认 `is_seekable: false` /
  `byte_len: None`,于是 symphonia 把流当只进不退,回跳一律 `ForwardOnly`。
  `decode` 现在收 `byte_len` 并从 `Content-Length` 传入。那是**能不能跳**的问题,
  本 ADR 说的是**怎么知道跳成没成**,两件事。
