# 歌单按数据主权切分:平台的归 go,自家的归 axum

日期:2026-08-01。状态:已采纳,其中「平台歌单一律直读、不落地」一条由
`docs/adr/0018` 修正为「留缓存,但平台仍是真相」。主权的切法不变。

## 背景

歌单功能横跨两个仓库,第一个要回答的问题是:歌单接口放 bang-dream(Go)还是
axum(Rust)。判据不该是「哪边代码好写」,而是**每份数据的真相在谁手里**。

## 决策

- **真相在平台的,走 bang-dream**:平台歌单、红心列表、每日推荐、搜索。
  bang-dream 保持纯防腐层定位,继续零业务落盘 —— 它自己的架构文档写着
  「不做曲库、收藏、播放历史」,这条不动。
- **真相在自家的,归 axum + Postgres**:本地歌单、播放事件、账号。
  bang-dream 永远看不到这些表。
- 客户端只认 axum 一个出口。两类歌单在 HTTP 契约层归一:一个 `PlaylistDto`
  带 `source` 字段(`netease` / `local`),操作的可用性由 source 决定 ——
  本地歌单可改名可删,平台歌单只能收藏/取消收藏。
- 「我喜欢的」**就是**平台红心列表,不建本地副本,在歌单列表里置顶、不可删。
  建副本等于给自己发明一个双写一致性问题。
- 播放历史只记事件流:起播即追加一条(谁、哪首、何时),不补记完成度。
  听歌统计是查询时的聚合,不建统计表、不跑定时任务 —— 口径想改就改,
  因为原始事件都在。

## 备选方案

**歌单全归 go,本地歌单做成"虚拟平台"实现 Provider。** 不选:Provider 接口
二十多个方法对本地歌单大半无意义,且破坏 go 的防腐层定位。

**歌单全归 axum,平台歌单也镜像进 Postgres。** 不选:镜像与网易云的一致性
(在手机官方 App 里改了歌单,这边何时看到)是永久背上的债,而直读没有这个问题。

## 代价

- 「我的歌单」页要聚合两个来源,axum 里多一层拼装。
- 平台歌单不落地,断网时列不出来 —— 与 `docs/adr/0015` 的取舍一致,离线那期统一解决。
