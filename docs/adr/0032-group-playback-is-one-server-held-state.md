# 组播放是服务端持有的一份全局状态,组里每台设备都能控制

日期:2026-09-26。状态:已采纳(#142)。取代 `0030`(遥控器模式与它的播放组、主端、共同计划);
修订 `0031` 第一、六节与文末两段 #137 修订。

## 背景

`0030` 那一套是「遥控器 → 被控端」的单向控制:服务端只转发,控制权是内存里的一个槽位,
组的时间线由成员里的**主端**写成共同计划发给其余成员。它在真机上暴露出三类问题(#142):

- 控制是单向的:被控端被锁住,坐在 pc1 前面的人按什么都不生效;
- 权威分散在几台设备和一个内存槽位之间:遥控器断线、服务端重启、主端失联,每一种都要一套
  租约、续权、代次、交接的补丁,补到 1 万行上下,仍有「谁也不放」「两台都以为自己是主端」;
- 点歌入口按「本机 / 遥控」分两条路,各入口实现不一致。

用户 2026-09-26 定的目标:**一份服务端全局播放状态,组内任何设备都能双向控制**。

## 决策

### 一、状态只在服务端,落库

每个账号至多一个组,一行 `play_groups`(`server/migrations/0009_play_groups.sql`):

- `members`:加入了组、能控制的设备;`outputs ⊆ members`:真正出声的那几台。
  「本机在组里」= 本机在 `members` 里。手机只当遥控器 = 在 `members` 不在 `outputs`。
- 此刻放的是组队列哪一版(`queue_id`、`revision`)的哪一条(`entry_id`);时间线是
  「挂钟 `anchor_wall_us` 这一刻媒体在 `position_us`」、在不在放、随机与循环、随机次序。
- `version`:每改一次加一,单调,组散了也不回退(不删行)。

时间线存**挂钟**而不是服务端单调钟:单调钟每次启动从零起,重启后换算不回来。发给客户端时
再换算成服务端单调钟(`GroupStateDto.clock_epoch` + 微秒时刻),客户端经校时换成本机时钟。

组里点的歌发布在伪设备 `group` 名下那一个队列的新版本上,与各台设备独奏时的队列分开
(`server::syncplay::group::GROUP_QUEUE_DEVICE`),回收孤儿队列时跳过组引用着的那一个。

### 二、意图走 HTTP,状态经信令广播

`GET /group`、`POST /group/play | transport | outputs | leave`(`contract::group`);电台续歌另有
`POST /group/append`(#165):往组此刻那一版的队尾追加、换到续上的那一版,在放的那一首与时间线不动。每一条意图
都是同一个形状:开事务 → 锁这一行 → 把放完的先往下推 → 应用意图 → 版本加一 → 写回 → 提交
→ 经名册把新状态(`ServerSignal::GroupState`)推给账号下每台在线设备。请求有明确的成败,
界面失败一律提示一句,不再静默丢弃。

信令只剩三件事:入册与名册、校时、出声设备每秒一条的执行事实(`Report` → `DeviceReport`,
原样转给同账号其余设备)。设备入册时服务端先推一份当前状态 —— 重连不需要任何「续权」。
协议版本 7。

### 三、谁都能控制,地位相同

组里任何一台设备的点歌(列表、卡墙、搜索、队列页)、⏯、上下首、拖动、随机、循环,都只改
这一份状态;本机在组里时一律不直接动本机播放器。「正被 xx 遥控」的锁与横幅删除,横幅改成
「与 X、Y 一起播放」。音量每台各自调,不进全局状态(远程看与调见第七节)。

**独奏保留**:不在组里的设备照旧本机放、本机队列,离线也能听(`0031` 第八节不变)。
建组:独奏时选了别的设备或按「+」,以本机正在放的那一份为种子(`GroupSeedDto`)。

**挂在死组上时点歌回落本机**(#165,用户 2026-09-28 定):本机在组里、而组的 `outputs` 没有一台
在线(本机算在线:信令连着),组里点歌哪儿都不响。这时点歌(含开电台)先 `leave`,退成了再按独奏在
本机放;退不成(离线等)提示「组里没有在线的出声设备」,横幅上那颗「退出」仍在。只在点歌那一下判,
有一台出声设备在线就照常走组意图。服务端规则(第五、六节)不变,成员不做超时清理。

### 四、出声设备照状态自己跟

出声设备看到状态里有自己:按 `queue_id`/`revision` 取执行副本(`0031` 第二节的「取全了再原子
换上」不变),把时间线换算到本机时钟交给音频层的跟随器(`audio::sync`),到锚点一起开始。
取不到、条目不在、媒体取不到,它报故障、不出声,不自己从头放、不换下一首。

**自动下一首由最先真正放完的出声设备触发**(AC-9):它把媒体放到真正的末尾,报
`POST /group/advance {entry_id, version}`;服务端按 `(version, entry_id)` 去重 —— 最先到的
推进,下一首一起开始(锚点怎么定见第八节),迟到的同一份报告作废,不加版本、不广播。状态里
预告的下一首(`next`)只是提示,设备不到点自己换(只拿它预加载,见第八节):按元数据时长换会截掉歌尾,或在歌尾留一段
空白。元数据时长只作兜底:放完之后再过 5 秒(`ADVANCE_GRACE_US`)还没有一台报,续播任务
(每 500ms 按 `boundary_wall_us` 挑)才自己推进。每新起一首服务端记一笔 `play_events`,
组里的设备不再各报一次。

### 五、掉线规则(用户 2026-09-26)

- 出声设备与服务端断开:**立刻暂停自己**,不按旧状态往下放;重连拿到最新状态再照着放。
- 最后一台在线的出声设备掉线或退出:服务端**立刻**把状态置为暂停,位置停在那一刻
  (出册时判定,沿用信令探活)。服务端自己挂掉时所有出声设备都在那一刻断开了:在放的组每
  2 秒记一次心跳(`play_groups.alive_wall_us`),重启时把还在放的组暂停在最后一次心跳那一刻。
- 出声设备重连之后把这一首按状态此刻的位置**重新起一遍**,不在停下的那个流上接着追:
  断开几十秒后输出流已经关了、媒体连接多半也断了,原地追赶会卡在停下的位置。
- 出声设备主动退出组:它自己停,其余照放。
- 只当遥控器的成员掉线:什么都不动。
- 离线期间在本机上的操作不重放,以服务端状态为准。

### 六、后来者加入(#149,用户 2026-09-27)

一台设备在组已经在放时才上线:入册时服务端照样推当前状态给它,但它不在 `members` 里,仍是
独奏,不自己跟着响。组**在播**时,它的组横幅写「组里正在播放: 歌名」,那颗键是「加入」。组暂停
着不挂入口:出声设备掉线后组只是停着、成员也不清理,挂着的话每台独奏设备上会一直有这条横幅。

- **加入**:`outputs = 组此刻的 outputs ∪ {本机}`,发 `POST /group/outputs`,不带种子。服务端
  把发的那台与新出声设备都记成成员;本机随即成了出声设备,按第四节取副本、按 `position_at`
  中途起播,本机原先独奏放的那一首让位。原有的出声设备状态没变,不停、不跳。
- **组已存在时的「+」与选设备**(本机独奏):同样是在组此刻的 `outputs` 上追加那一台,不拿本机
  播放拼一份新列表整体覆盖 —— `set_outputs` 是整体替换,覆盖会把原来出声的设备挤成哑成员。
  独奏时芯片上不标组的出声设备,所以这时的「+」只加不移出。
  拼出来的 `outputs` 里原有的出声设备此刻不在线的,服务端直接剔掉而不是整条拒掉(#165):换了 id
  的开发实例、没人用的旧设备会永远挂在 `outputs` 里,留着它每一次加入都 400。新点的那台不在线仍拒。
- **组不存在**(状态里没有 `now`)时照旧:以本机正在放的那一份为种子建组(第三节)。

被否决:新设备上线就自动加入。每台设备一开就跟着响,用户选了手动入口。

### 七、音量(#151,用户 2026-09-27)

音量仍是每台各自的(外放和耳机不该共用一个数),真相在各台本机的设置里,不进 `play_groups`,
也不进版本化的组状态。但组里任何一台都看得见、调得动每台出声设备的音量(类似 Sonos):

- **看**:出声设备每秒那条执行事实(`DeviceReportDto`)带上本机音量,服务端照旧原样转给同账号
  其余设备。输出设备那一排,正在出声、报过音量的那台各有一条音量条;本机的音量在它上面那一行。
- **调**:拖别台的音量条发信令 `SetVolume { to, volume }`,服务端**只转给 `to` 那一台**
  (`ServerSignal::SetVolume { from, volume }`),不在线就回一条 `offline` 错误。目标照本机拖滑块
  那条路应用:夹值、设播放器、节流存盘,新值在它下一条执行事实里带回给大家。发的那台的音量条
  先跟手,之后以回报为准。
- 协议不升版:全是增量,旧端只是不出音量条、调不动(`contract::PROTOCOL_VERSION` 的说明)。

被否决:把各台音量放进组状态(`GroupStateDto`)。组状态每改一次加一个版本、落库、客户端只收
更新的版本;音量既然不是组的真相,放进去就要么每拖一下滑块加一个版本广播一遍,要么让客户端
收同版本的「只改了音量」—— 两样都比借已经每秒一条的执行事实贵。代价是新上线的设备最迟一秒
后才看到别台的音量。

### 八、起播等出声设备就绪(#154,2026-09-27)

0.1.24 现场每次切歌都有一条 `原因 Entry` 的跳转,误差 -1.2s 到 -6.0s:下一首锚在「现在 +
500ms」,出声设备拿到状态后才取直链、建连、预取开头,要两到四秒,好了时时间线已经走出几秒,
开头就被跳过去。两处一起改:

- **预加载**:出声设备放当前这首放过十秒(与独奏预取同一个门槛),就按状态里的 `next` 把那一首
  备好(取直链、开流、解码器就位)。切歌时起播直接用备好的,几十毫秒就能出声。独奏照旧备本机
  队列的下一首;只当遥控器的不备。
- **新起一首先锚远一点,都就绪了再提前**:点歌、上下首、放完推进、兜底推进,锚点先定在
  「现在 + 3 秒」(`timeline::START_WAIT_US`)。出声设备把那一首备好、起播还没到时,报
  `POST /group/ready {entry_id, version}`。**在线**的出声设备都报过这一版,服务端就把起播提前到
  「现在 + 500ms」(`LEAD_US`)、加版本、广播;只往前挪,已经开走的、暂停着的、报的不是此刻那
  一版那一条的,都不动。
- **多台时等谁**:等在线的全部出声设备,「一起响」是组的前提,先好的那台先响就不叫一起了。
  掉线的不等(按名册判在线);一台卡住、一直不报,3 秒一到照常开播,它自己追上来 —— 3 秒
  就是上限,锚点一开始就落在那里,不需要另外的超时任务。
- 就绪集合只在服务端内存里,按账号记「哪一版、哪几台」,版本一变整份作废。服务端在等待中
  重启,也只是等满 3 秒。就绪是出声设备的执行报告,与队列报告同一道限流闸,不占人按的意图额度。
- 跳转与继续仍锚在「现在 + 500ms」:手上已经有流,通常等不了多久。旧客户端不报就绪,和它
  一起出声的组每次切歌都等满 3 秒 —— 协议不升版,换版时两端一起换。

被否决:

- **锚点不预先定,等就绪了才定**(状态里先挂一个「未开始」):要给状态加一个新形态,遥控器、
  进度条、兜底推进、掉线暂停都要认它;超时还得另起任务去推。锚点先落在上限处,每一处现有
  的规则都照旧成立。
- **只按最先就绪的那台开走**:慢的那台开头照样被跳过,只是从组的视角看不出来。
- **只靠预加载**:用户临时点别的歌、连按下一首时没有预加载可用,还是会被吃掉开头。

## 后果

- 删掉了控制权槽位、租约与代次、迁移的四步确认、主端任期与交接、共同计划、被控锁与
  `RemoteView` 镜像(`server/src/syncplay/control.rs`、`app-core` 的 `session.rs`/`output.rs`/
  `group.rs`、`ui` 的 `sync/remote.rs`/`migrate.rs`),约 1 万行。
- 组播放从此硬依赖服务端:服务端不可达时组内操作全部失败并提示,出声设备暂停。独奏不受影响。
- 协议断代(7),旧客户端握手即被拒,桌面与安卓要一起换版本。
- 服务端重启不丢组:状态在库里,版本号接着数;客户端重连后收到当前状态照着做。

## 被否决的做法

- **在 `0030` 上继续打补丁**(断线租约、续权、核权、重新认领):#142 第一版就是这么做的,
  8 个提交里 6 个随本篇作废(以 revert 留在分支历史里)。每一种失效方式一套补丁,补丁之间
  还要互相兼容。
- **主端写计划、服务端只转发**:权威在某台设备上,它一失联就要选新主端或停下;服务端既然要
  持有队列(`0031`),多持有一个时间线并不更贵。
- **只按元数据时长由服务端推进**(第一版实现):元数据时长与真实媒体长度常差一两秒,
  换歌时刻会截掉歌尾或留空白。改成出声设备真正放完才推进,时长只作兜底(#142 AC-9)。
- **客户端确定性洗牌**(设计稿的写法):次序由服务端洗好存在 `play_order` 里,客户端只照着
  放,不必两端逐位一致地复算。
- **所有出声设备离线后等 60 秒再暂停**:用户定为立刻暂停。
