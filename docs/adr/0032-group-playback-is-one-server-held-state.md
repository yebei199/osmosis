# 组播放是服务端持有的一份全局状态,组里每台设备都能控制

日期:2026-09-26。状态:已采纳(#142)。取代 `0030`(遥控器模式与它的播放组、主端、共同计划);
修订 `0031` 第一、六节与文末两段 #137 修订。

## 背景

`0030` 那一套是「遥控器 → 被控端」的单向控制:服务端只转发,控制权是内存里的一个槽位,
组的时间线由成员里的**主端**写成共同计划发给其余成员。它在真机上暴露出三类问题(#142):

- 控制是单向的:被控端被锁住,坐在 pc1 前面的人按什么都不生效;
- 权威分散在几台设备和一个内存槽位之间:遥控器断线、服务端重启、主端失联,每一种都要一套
  租约、续权、代次、交接的补丁,补到 1 万行上下,仍有「谁也不放」「两台都以为自己是主端」;
- 点歌入口按「本机 / 遥控」分两条路,各入口实现不一致。

用户 2026-09-26 定的目标:**一份服务端全局播放状态,组内任何设备都能双向控制**。

## 决策

### 一、状态只在服务端,落库

每个账号至多一个组,一行 `play_groups`(`server/migrations/0009_play_groups.sql`):

- `members`:加入了组、能控制的设备;`outputs ⊆ members`:真正出声的那几台。
  「本机在组里」= 本机在 `members` 里。手机只当遥控器 = 在 `members` 不在 `outputs`。
- 此刻放的是组队列哪一版(`queue_id`、`revision`)的哪一条(`entry_id`);时间线是
  「挂钟 `anchor_wall_us` 这一刻媒体在 `position_us`」、在不在放、随机与循环、随机次序。
- `version`:每改一次加一,单调,组散了也不回退(不删行)。

时间线存**挂钟**而不是服务端单调钟:单调钟每次启动从零起,重启后换算不回来。发给客户端时
再换算成服务端单调钟(`GroupStateDto.clock_epoch` + 微秒时刻),客户端经校时换成本机时钟。

组里点的歌发布在伪设备 `group` 名下那一个队列的新版本上,与各台设备独奏时的队列分开
(`server::syncplay::group::GROUP_QUEUE_DEVICE`),回收孤儿队列时跳过组引用着的那一个。

### 二、意图走 HTTP,状态经信令广播

`GET /group`、`POST /group/play | transport | outputs | leave`(`contract::group`)。每一条意图
都是同一个形状:开事务 → 锁这一行 → 把放完的先往下推 → 应用意图 → 版本加一 → 写回 → 提交
→ 经名册把新状态(`ServerSignal::GroupState`)推给账号下每台在线设备。请求有明确的成败,
界面失败一律提示一句,不再静默丢弃。

信令只剩三件事:入册与名册、校时、出声设备每秒一条的执行事实(`Report` → `DeviceReport`,
原样转给同账号其余设备)。设备入册时服务端先推一份当前状态 —— 重连不需要任何「续权」。
协议版本 7。

### 三、谁都能控制,地位相同

组里任何一台设备的点歌(列表、卡墙、搜索、队列页)、⏯、上下首、拖动、随机、循环,都只改
这一份状态;本机在组里时一律不直接动本机播放器。「正被 xx 遥控」的锁与横幅删除,横幅改成
「与 X、Y 一起播放」。音量每台各自调,不进全局状态。

**独奏保留**:不在组里的设备照旧本机放、本机队列,离线也能听(`0031` 第八节不变)。
建组:独奏时选了别的设备或按「+」,以本机正在放的那一份为种子(`GroupSeedDto`)。

### 四、出声设备照状态自己跟

出声设备看到状态里有自己:按 `queue_id`/`revision` 取执行副本(`0031` 第二节的「取全了再原子
换上」不变),把时间线换算到本机时钟交给音频层的跟随器(`audio::sync`),到锚点一起开始。
取不到、条目不在、媒体取不到,它报故障、不出声,不自己从头放、不换下一首。

**自动下一首由最先真正放完的出声设备触发**(AC-9):它把媒体放到真正的末尾,报
`POST /group/advance {entry_id, version}`;服务端按 `(version, entry_id)` 去重 —— 最先到的
推进,下一首锚在「现在 + 500ms」一起开始,迟到的同一份报告作废,不加版本、不广播。状态里
预告的下一首(`next`)只是提示,设备不到点自己换:按元数据时长换会截掉歌尾,或在歌尾留一段
空白。元数据时长只作兜底:放完之后再过 5 秒(`ADVANCE_GRACE_US`)还没有一台报,续播任务
(每 500ms 按 `boundary_wall_us` 挑)才自己推进。每新起一首服务端记一笔 `play_events`,
组里的设备不再各报一次。

### 五、掉线规则(用户 2026-09-26)

- 出声设备与服务端断开:**立刻暂停自己**,不按旧状态往下放;重连拿到最新状态再照着放。
- 最后一台在线的出声设备掉线或退出:服务端**立刻**把状态置为暂停,位置停在那一刻
  (出册时判定,沿用信令探活)。服务端自己挂掉时所有出声设备都在那一刻断开了:在放的组每
  2 秒记一次心跳(`play_groups.alive_wall_us`),重启时把还在放的组暂停在最后一次心跳那一刻。
- 出声设备重连之后把这一首按状态此刻的位置**重新起一遍**,不在停下的那个流上接着追:
  断开几十秒后输出流已经关了、媒体连接多半也断了,原地追赶会卡在停下的位置。
- 出声设备主动退出组:它自己停,其余照放。
- 只当遥控器的成员掉线:什么都不动。
- 离线期间在本机上的操作不重放,以服务端状态为准。

## 后果

- 删掉了控制权槽位、租约与代次、迁移的四步确认、主端任期与交接、共同计划、被控锁与
  `RemoteView` 镜像(`server/src/syncplay/control.rs`、`app-core` 的 `session.rs`/`output.rs`/
  `group.rs`、`ui` 的 `sync/remote.rs`/`migrate.rs`),约 1 万行。
- 组播放从此硬依赖服务端:服务端不可达时组内操作全部失败并提示,出声设备暂停。独奏不受影响。
- 协议断代(7),旧客户端握手即被拒,桌面与安卓要一起换版本。
- 服务端重启不丢组:状态在库里,版本号接着数;客户端重连后收到当前状态照着做。

## 被否决的做法

- **在 `0030` 上继续打补丁**(断线租约、续权、核权、重新认领):#142 第一版就是这么做的,
  8 个提交里 6 个随本篇作废(以 revert 留在分支历史里)。每一种失效方式一套补丁,补丁之间
  还要互相兼容。
- **主端写计划、服务端只转发**:权威在某台设备上,它一失联就要选新主端或停下;服务端既然要
  持有队列(`0031`),多持有一个时间线并不更贵。
- **只按元数据时长由服务端推进**(第一版实现):元数据时长与真实媒体长度常差一两秒,
  换歌时刻会截掉歌尾或留空白。改成出声设备真正放完才推进,时长只作兜底(#142 AC-9)。
- **客户端确定性洗牌**(设计稿的写法):次序由服务端洗好存在 `play_order` 里,客户端只照着
  放,不必两端逐位一致地复算。
- **所有出声设备离线后等 60 秒再暂停**:用户定为立刻暂停。
