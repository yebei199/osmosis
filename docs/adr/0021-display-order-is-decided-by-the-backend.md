# 平台歌单的展示次序由后端决定,排序键换成加入时间

日期:2026-08-09。状态:已采纳。修正 `docs/adr/0018` 的一条隐含约定。

## 背景

`docs/adr/0018` 建的 `platform_playlist_tracks` 用 `position` 承载次序,而
`position` 就是平台返回数组的下标。建表注释把这条写死了:「歌单内的次序。
平台给的顺序是有意义的,丢了用户的歌单就乱了」。

红心这边这条不成立。它的曲目标识来自网易云的 `/api/song/like/get`,那个接口
返回的是**裸数字数组** —— 结构上挂不住任何时间戳,顺序稳定却不表示任何东西。
实测一个 976 首的红心列表:按加入时间排最新的那一首(当天上午刚点的),在这个
数组里排第 120 位。「顶部是最新收藏」这个预期在这个接口上没有落脚点,不是排序
坏了,是这个数组本来就不按时间排。

同一个平台在另一个接口上给了答案:歌单详情的 `trackIds` 元素带 `at`,毫秒级,
逐条唯一,就是这首歌被加进这个歌单的时刻。平台自己按它倒序发。这个字段一直
都在,只是解析时连同其余字段一起丢掉了。

## 决策

`platform_playlist_tracks` 增列 `added_at`,值取平台的 `at`。平台歌单的展示
次序由后端决定:

```
ORDER BY added_at DESC NULLS LAST, position ASC
```

`position` 的含义不变,仍是平台返回数组的下标。它降为第二排序键,负责
`added_at` 相同或缺失时的稳定次序 —— 老数据回填之前走的正是这条路。

界面可以按歌单切回平台原序。这个选择**只存偏离默认的那些**(见
`crates/api/src/settings.rs`):没改过的歌单不占位置,那张表不会随歌单数增长。

`docs/adr/0018` 的三条规矩一条没破:排序键 `added_at` 来自平台,不是本地记的;
写仍然直发平台;缓存整张删掉重刷一次能完整还原。被修正的是比规矩更弱的一条
**隐含约定** —— 「平台给的数组顺序是有意义的」。它对经营过的歌单成立,对红心
不成立,而两者共用一张表。

## 备选方案

**本地记录点红心的时刻。** 不选:那个时间戳平台没有,删掉缓存就永久丢失 ——
按 0018 规矩 3 的判定问题,它已经不是缓存了。何况它只盖得住自家 app 里点的,
在官方 App 里点的红心永远浮不上来,而那正是用户最常抱怨的那个场景。

**只改红心,别的平台歌单保持原序。** 不选:`tracks_of` 是一个查询服务所有平台
歌单,分叉出去就要长期维护两条读路径与两套测试。代价见下 —— 这一条是真的有
代价,不是白拿的。

**不动顺序,加列表内搜索。** 不选:找得到不等于顺序对。红心是最常进的那个歌单,
每次都要先搜一遍才能看到刚加的歌,那是把问题挪了个地方。

## 代价

- **订阅来的歌单会被重排**。它们的 `at` 是原作者往里加曲目的时刻,不是使用者的。
  按它倒序,专辑式歌单接近倒放,白噪音这类靠编排的歌单会乱。界面开关是唯一的
  出口,而用户要自己找到它。这是本次决策最贵的一项。
- 多一列、多一条索引。刷新时多写一个字段。
- `position` 从「唯一的排序键」降为「兜底的排序键」。`0004` 的建表注释与
  `cache.rs` 的函数文档都要跟着改,否则读代码的人会按旧的读法理解它。
- 平台不给 `at` 的歌单(或将来的第二个平台)落到 `NULLS LAST`,退回平台原序。
  那是可用的降级,不是错误 —— 但它意味着同一个列表里可能混着两种次序。
