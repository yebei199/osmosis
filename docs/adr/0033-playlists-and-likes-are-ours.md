# 歌单与红心归我们,平台只是音源

日期:2026-09-26。状态:已采纳(#146)。取代 `docs/adr/0016` 里「我喜欢的就是平台
红心列表,不建本地副本」一条与平台歌单归平台的那半;取代 `docs/adr/0018` 里与歌单、
红心相关的条款。`0018` 那份平台曲目**详情**的缓存照旧。

## 背景

`0016` 与 `0018` 的立场是「平台是真相」:界面上的歌单大多是网易云的,直读网易云,
Postgres 里只缓存一份;「我喜欢的」就是网易云的红心列表,点红心直接写网易云。

用户 2026-09-26 改了方向:osmosis 自己持有曲库。网易云只是一个音源,以后还会接
B 站、抖音这类音源;歌单和红心这套东西归我们。用户账号下 35 个网易云歌单、去重后
3356 首,用户说其余的都不听,只要红心。

## 决策

主权重新划分:

- **歌单与红心归我们**,真相在自家 Postgres。歌单页只列我们自己的歌单。
- **平台只是音源**:给播放地址、曲目详情、歌词、搜索结果。曲目仍用
  `(平台, 平台内 id)` 标识,换成自有曲目 ID 是后续阶段的事。
- **每日推荐暂时仍由平台提供**,是目前唯一一项。里面的歌照样能点红心加进「我的喜欢」。

落地:

- 「我的喜欢」是一个**系统自带的本地歌单**,建在 `0002_local_playlists` 那两张表上,
  用 `local_playlists.system = 'liked'` 认(迁移 0011)。每个账号一个,不可删、
  不可改名,在歌单列表里置顶。普通歌单的列表、改名、删除都认不出它。
- **红心与取消红心只改这一份**,不写回网易云。
- 网易云的红心**导一次**(`POST /liked/import`),保留原次序与加入时刻;之后以我们的
  为准。同一条路由也是手动的「再导一次」:只补新增,不删除,重跑不重复。界面上没有
  按钮。平台一时给不出详情的曲目照样导进来,读的时候算作不可用 —— 成员关系是我们的。
- `/playlists` 只返回「我的喜欢」与本地歌单。网易云歌单(含收藏的)从应用里移除,
  不再列出、不再同步;网易云账号里的原样不动。搜出来的平台歌单仍可点进去听,那条
  路还按 `0018` 的缓存规矩走。
- 存进对象存储的曲目(#126)按这份红心决定留不留。

### 协议

线上形状一个字段都没变:`/playlists` 仍给 `PlaylistDto` 列表、「我的喜欢」仍用
`source: liked`,`/liked`、`/liked/ids`、`PUT|DELETE /liked/{id}` 路径与响应体照旧。
旧客户端照常工作,只是看不到平台歌单了。`PROTOCOL_VERSION` 不动(#142 的那套只管
信令)。「我的喜欢」这个名字由服务端给,客户端不写死。

## 备选方案

**「我的喜欢」单开一张表。** 不选:它就是一个歌单,单开表就得为它单写一套读写与
测试。系统歌单用一列认,普通歌单的查询加一个 `system IS NULL` 就把它挡在外面。

**继续双写网易云。** 不选:用户定了以我们的为准。双写就是 `0016` 当初拒绝的那个
一致性问题,而这次真相已经在我们这边,写回去换不来任何东西。

**首次打开时自动导入。** 不选:导入要向平台要近千首,把它挂在一次读上,那一次就
可能超时;而用户要的是「导一次」,一条显式的路由正好是那一次。

## 代价

- 在网易云官方 App 里新点的红心不会自动出现在我们这边,要手动再导一次。再导不删
  东西,所以在这边取消过、网易云那边还红着的歌,再导会回来。
- 收藏的网易云歌单在应用里看不到了。要留哪首,先点红心。
- `bangdream::platform_playlists_to_dto` 与平台歌单的收藏路由暂时没人用,留着待清。
