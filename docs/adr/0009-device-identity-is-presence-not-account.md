# 设备身份是自报的在线标识,不是账号

日期:2026-07-27。状态:已采纳。

## 背景

同播需要回答「谁是谁」:主控要能列出可推送的设备,信令要能寻址到具体一台。
最初的设想是给 axum 做一套注册登录,但捋清使用场景后发现:本系统只有一个用户
(服务不出内网,调用方全是自己的设备),缺的从来不是「用户是谁」,而是「设备是哪台」。

**设备标识与设备认证是两件事。** 前者回答「这台是客厅平板」,同播必需;
后者回答「这台有没有资格连」,单人内网场景里暂时没有敌人。

## 决策

- 每台设备首次启动时自己生成 id,连同一个人读的名字存在本地(与 bang-dream 保存
  自己那份设备指纹是同一个模式,但两个概念无关,见 `CONTEXT.md`「设备 (Device)」)。
- 设备连上 axum 的 WebSocket 时自报 id + 名字。服务端信任自报,不验证。
- **axum 不持久化设备。** 在线设备列表就是当前活跃的 WS 连接集合,断开即消失。
  没有设备表、没有数据库、没有任何落盘。离线设备本来就无法参与同播,记住它没有用处。
- **注册/认证被刻意推迟。** 将来若要开门到内网之外,认证是给「建立连接」这一步加
  一道门禁 —— 模型里已有设备这个单位,加门禁不需要动它。

## 备选方案

**现在就建 user + device 两层。** user 表里躺一行,为将来的多用户预留外键。
不选:那一层眼下没有任何消费者,是纯粹的推测性结构;真到多用户那天,
「设备属于谁」的问题才第一次存在,到时候再回答它。

**预共享密钥。** 每个请求带一个配置里的固定密钥,换取监听 0.0.0.0 的安心。
不选,但记录在案:这是将来第一个值得加的门禁形态,一列配置 + 一个中间件的事。

## 代价

- 服务端信任自报身份,任何能连上端口的进程都可以冒充任何设备。当前监听
  `127.0.0.1` + `adb reverse`,风险面是本机;若改为监听局域网,应先补门禁。
- 设备改名、换 id 无迹可查 —— 服务端没有记忆,也就没有历史。
- 「见过但不在线」的设备列不出来。同播场景不需要它;哪天需要(比如远程唤醒),
  持久化才第一次有消费者。
