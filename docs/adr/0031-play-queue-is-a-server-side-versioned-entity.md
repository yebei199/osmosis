# 播放队列是服务端的持久实体,播放端手上那份是执行副本

日期:2026-09-21。状态:已采纳。2026-09-24 修订(#137 ③,见文末「#137 ③ 修订」);
2026-09-25 修订(#137 ⑤ 多成员,见文末「#137 ⑤ 修订」)。修正 `0030` 第二、三、四节;不推翻 `0018`
的三条缓存规矩,只补上队列与缓存的关系。

## 背景

遥控器模式(`0030`)把**整批曲目**放进信令载荷,而信令通道是按 SDP 与 ICE
设计的,`contract::MAX_SIGNAL_BYTES` 是 64 KiB。两个方向都压在这条线上:

| 方向 | 载荷 | 977 首时 | 频率 |
|---|---|---|---|
| 出站 `RemoteCommand::Play` | 整批 `TrackDto` | 238350 字节(真机 224194) | 每次点歌 |
| 入站 `RemoteStateDto.queue` | 被控端的整个队列 | 238655 字节 | **每秒一次** |

越界点实测 269 首 —— 随手一个专辑合集就过了。**超限的后果不是丢一条消息**:
tungstenite 读到超长消息返回 `Capacity(MessageTooLong)`,服务端读循环那句
`let Some(Ok(message)) = incoming else { break }` 直接跳出,整条连接断掉,
随后走出册与控制权清理。出站超限撕掉连接,入站超限让被控端把自己出册、
释放控制权槽位。

抬高那个常量治标不治本(五千首照样炸,而且每条连接的服务端缓冲跟着抬),
按字节剪批次是悄悄改产品含义。真正大的载荷该换一条路走。

用户 2026-09-21 定下的目标不止「别炸」:**播放队列持续存在于后端数据库**,
且**所有播放都走它**,不只遥控会话。跨设备续播不在本轮。

## 决策

### 一、三层裁决分开,不许混成一层

| 层 | 内容 | 谁是权威 |
|---|---|---|
| 队列定义 | `queue_id`、`revision`、有序且**允许重复**的条目、循环与随机规则 | **服务端**,事务提交 |
| 待应用的播放意图 | 目标播放会话、`queue_id`/`revision`、选中 `entry_id`、`operation_id`;可为 pending 或 failed | 服务端存 |
| 实际执行状态 | 已应用 `revision`、当前 `entry_id`、实际播放次序与循环轮次、`position_ms`、playing/buffering/paused | **播放端**;服务端存的是它最近确认的那份记录 |

界面必须分得清「新版本待应用」与「已经出声」。数据库里写了不等于音箱在响 ——
拿前者冒充后者,遥控器上会出现一个自己往前爬、又在下一次上报时跳回去的进度条,
而那是最难查的一类错。

### 二、队列的身份:`queue_id` + `revision` + `entry_id`

逻辑 `queue_id` 持续存在,修改**原子产生新 `revision`**。一次分页读取固定在
一个 `revision` 上,不会前半页旧顺序、后半页新顺序。

`entry_id` 区分同一首歌在队列里重复出现的不同位置。队列**允许重复**,所以
它不能复用现有歌单那个「同曲唯一」的主键(`local_playlist_tracks` 与
`platform_playlist_tracks` 都是那个形状)。**展示原序与播放顺序分开保存。**

`entry_id` 在同一个 `queue_id` 内**跨 revision 稳定**:新版本沿用旧条目的
`entry_id`,只有新插入的条目才拿新号。不稳定的话,播放端手上
`applied_revision = 5, entry_id = X` 与服务端的 revision 6 根本对不上账,
而对账正是持久化新增复杂度的全部所在。

**队列归属于一个播放会话 / 输出设备,不是拿 `account_id` 当唯一当前队列。**
否则同账号两台设备各自本机播放会互相覆盖。持久队列身份、设备身份、一次执行
会话的身份是三样东西,不能混用;「每账号一个遥控控制槽」也不等于「每账号
只准有一个播放队列」。

### 三、曲目数据走 HTTP,信令只走小消息

- **每秒小状态**:`queue_id`/`revision`、`applied_revision`、执行会话标识与
  递增 `state_seq`、当前 `entry_id`、队列长度、`position_ms`、`state`、`volume`,
  以及有大小约束的当前曲目展示摘要。字节数**不随队列长度增长**。
- **队列数据**:取得控制权、换目标、队列版本变化、或本地缓存缺失时,按
  `queue_id`/`revision` 经 HTTP 拉一次。队列没变就零次重传。

顺序判定用执行会话标识加递增 `state_seq`、外加本地接收时间,不再把跨重启的
挂钟当唯一顺序依据。状态新鲜度与队列加载状态**分开**:小状态到达就该知道
远端在放什么,列表还没下完时显示加载,不能一直假装「正在连接」。

遥控器持有的是**只读显示缓存**,不是另一份队列真相:不能用它上传的候选列表
冒充播放端已接受的列表,也不能本地决定下一首。

数据量大靠分页与有界上传加事务式发布,**不退回 WebSocket 传长 id/order 数组**。
超出约定规模时明确拒绝,不截断、不静默。第一版不做任意增量编辑协议;以后测到
队列编辑频繁,再加带 `base_revision` 的增量,丢失时回退整份快照。

### 四、红线:自动下一首不得依赖服务端事务批准

给续播加一个实时数据库依赖,与「播放端自主推进」这条产品保证直接冲突。播放端
事先取得完整队列与足够的执行信息,断连时照样在**已应用版本**上推进。

### 五、队列条目自己持久化,与平台缓存分家

条目字段:`entry_id`、`platform`、`track_id`、位置,以及**创建该版本时的展示
信息快照**(标题、别名、歌手、时长)。封面 URL 即使存了也不保证永久有效;
**临时播放直链一律不作为永久资源保存**。

- 队列条目**不外键指向 `platform_tracks`**,既不 `ON DELETE CASCADE`
  也不 `RESTRICT`——前者让清缓存删掉用户的队列,后者把缓存钉死成不可删。
  现有 `platform_playlist_tracks -> platform_tracks` 的 CASCADE 保留,
  它们同属可重建的缓存。
- **清缓存不能删除队列条目、不能改变顺序、不能把重复项合并。**
- 缓存缺失时回平台取详情只是**恢复优化**,不是保存用户队列的唯一保障:曲目会
  下架、平台会故障、权限会失去。那时保留条目身份、位置与最后已知展示信息,
  **显示不可用** —— 不能像歌单刷新那样把缺详情的曲目从队列里剔掉。
  **能保存队列不等于能保证歌曲将来还能播。**

不必无限保留版本,但**已被执行端采用的、以及仍在被读取的版本不能回收**。
不再把「活跃队列 TTL 到期后靠播放器重新发布」当作主恢复路径。

来源(搜索、推荐、歌单)不作为队列的定义:查询时刻、缓存刷新、排序都会改变
结果,而 `tracks_of` 按「最近加入的在最前」排(`0021`)、`set_membership`
刷新时先删后重写。**点播那一刻把用户实际看到并选择的有序条目冻结成一个
revision**,来源参数只作来源说明,不能用来重跑查询重建队列。

### 六、洗牌与回卷:规则属于定义,排列属于执行状态

基础条目顺序与循环/随机**规则**是队列定义的一部分;实际 `order`、当前游标、
循环轮次是**执行状态**,由唯一播放端产生并报告,可作为恢复检查点存后端。

**显式保存排列与 `entry_id` 的对应关系**,不让两端只凭 seed 猜。大 `order`
走 HTTP,在洗牌或回卷变化时同步,每秒那条只报它的版本、轮次与位置。
自动下一首**不等**检查点落库;断连时后端的 `order` 可能旧,必须标陈旧 ——
不能同时承诺「断网自主续播」和「服务端永远实时拥有精确 order」。

现有语义原样保留:`Queue::next` 在列表循环末尾调 `rewind`,随机**每轮重新洗**,
而开随机时只洗未播放的那一段(`app-core/src/queue.rs`、`CONTEXT.md`「队列」)。
只保存第一次排列会悄悄改变它。

### 七、失败与恢复:持久化真正新增的那部分

有现成的表只省掉存储那一层,下面这些一条都免不掉:

- **HTTP 已提交、WebSocket 通知丢了或服务端随后重启,不能永久失去该变更。**
  服务端持久保存期望版本与待应用操作,WebSocket 只作唤醒通知;播放端恢复时
  读取并对账。
- **`desired_revision` 与 `applied_revision` 分开。** 下载失败保留旧执行副本,
  新请求标失败或待重试,**不能谎报已应用**。
- 更新带 `expected_revision`、`operation_id`,以及控制会话代次与执行端 epoch:
  旧请求、重复请求、旧执行端的迟到报告都不能覆写新状态;服务重启后的 epoch
  不能错误复用。
- **不自动重放过期的「开始播放」意图。** 持久队列不等于重启后自动出声:
  服务恢复时先重新确认执行权,再处理有效操作。
- 断连时执行端只在已应用版本上推进,不偷偷编辑共享队列成员,重连后也不能拿
  整个本地副本覆盖服务端的新版本。
- 取数据失败保留原队列,**不执行半份列表**;连点 A、B 时迟到的 A 不覆盖 B;
  重试同一 `operation_id` 不再次重置播放;下载期间失权、换目标、退出被控
  都让旧操作失效。

### 八、离线与失败不得挡住本机播放

「所有播放都持久化」不等于「写不进服务端就不许放歌」——一个音乐播放器在服务端
不可达时点不动歌是重大回退。本机点播的形状是:**本地先行起播,队列提交异步
进行**;提交失败不挡播放,但要标出「未同步」,恢复后对账。

## 后果

- `PROTOCOL_VERSION` 2→3:`RemoteCommand::Play` 改必需字段、`RemoteStateDto`
  删 `queue`,两样都是不兼容变更。光改常量不够 —— 版本比对此前只发生在
  `/health`,`/signal` 的握手没有版本检查,旧客户端照样连得上、两边遇到不认识
  的 JSON 默默丢弃。要真拒绝不兼容端,得在**取得控制权之前**加握手协商,
  并且让版本错误与普通掉线在界面上分得开。
- 一次桌面、安卓、服务端的协调升级,不维护长期双协议。web 按 `#105` 继续冻结,
  不为它维持旧遥控协议。
- 普通本机点播多一次写入与一道失败门槛。这是用户可见的产品选择,已由用户明确
  选定,并以上面第八条兜底。
- 服务端从「不解释载荷」变成「解释并持有队列」。`0030` 第三、四节据此改写 ——
  它对 `Signal{to, payload}` 仍然成立,对队列不再成立。
- 多一类要回收的数据。回收策略必须绕开「仍在被读取」与「已被采用」两种版本,
  而这两种都不能只靠 TTL 判断。

## 被否决的做法

- **抬高 `MAX_SIGNAL_BYTES`**:治标不治本,五千首照样炸,每条连接的服务端
  缓冲上限跟着抬。
- **遥控器侧按字节剪批次**:悄悄改了产品含义。超限要明确拒绝,不要截断。
- **裸来源描述符**(发搜索词 / 推荐日期 / 歌单 id 让对端重跑查询):查询时刻、
  缓存刷新、排序都会改变结果,拿它当队列,刷新一次正在放的东西就可能被改掉。
  本篇采纳的不是这一条 —— 冻结的是用户点下那一刻的有序条目,不是一个会被
  重跑的查询。
- **传 id 列表让被控端自己取**:id 列表仍随曲目数增长,一样会超限;还要处理
  缺失曲目、重复项、平台命名空间与顺序保持。是体积优化,不是架构。
- **在同一条 WebSocket 上做分片子协议**:64 KiB 限的是完整 message 不是 frame,
  原生分帧最后仍合并计数。要分片就得拆成多条独立应用消息,那需要分块确认、
  流量控制、重组资源上限、超时、取消、原子应用、断线恢复与控制消息调度保障,
  而服务端 `OUTBOX_CAPACITY = 32` 的尽力投递承担不了。「少改服务端」这个优势
  不成立。
- **服务端只存不可变快照、不裁决当前队列**(`#109` 初版的 R4):HTTP 数据通路、
  按确定版本读取、WebSocket 只走小消息、原子应用这四样全部保留,改变的是
  服务端成为队列定义与已提交版本的权威 —— 因为用户新提出的目标是**持久队列**,
  而不是「让大载荷换条路走」。

## #137 ③ 修订(2026-09-24):单成员过渡状态

三层权威原样保留,第三层(实际执行)改为:**组主端决定共同计划,每个成员报告
自己执行的事实**。本轮组的成员至多一台,它就是主端,所以 `applied_revision`
仍由那一台报 —— 但它是**成员的** observed,不是全组的一个标量,⑤ 加成员时每台
各报各的。**多台同时出声尚未交付**(#137 ⑤)。

跟着变的三处:

- **迁移按标识交接**:选设备时源的队列以 `queue_id` / `revision` / `entry_id`
  交给目标,目标照第二节「取全了再原子换上」取整份执行副本(`0030` 第六节)。
  不传曲目、不传半份。
- **发布直接带回条目号**:`POST /queues` 与 `POST /queues/{id}/revisions` 的应答
  多了 `entry_ids`(按位置排)。点播的那一端不再为了找「第 i 条是哪个条目」把
  整份队列分页读回来 —— 那是 5000 首十次往返、每页带全部展示信息,只为一列 i64。
  被控端仍然取整份执行副本(完整副本与失败原子性不变)。
- **同一批不重复发布**:同一台设备、同一批曲目再点一首,沿用上一次发布的那一版,
  只换条目;本机同一批已同步时只记一笔检查点。版本号不再随连点一路往上推。

## #137 ⑤ 修订(2026-09-25):多成员

第三层(实际执行)在多成员下落成两半,各有各的权威:

- **共同计划归组主端**(`contract::GroupPlanDto`):放哪个队列(`queue_id`)的哪一版
  (`revision`)的哪一条(`entry_id`)、那一刻媒体在哪、预告的下一首、播放次序与循环模式。
  只有当前主端、当前任期发的计划才被转发和采纳,旧任期、旧序号、旧纪元(服务端重启前的
  时刻)的一概不生效(`0030` 第七节)。
- **执行的事实归每个成员**:每台各报各的 `applied_revision`、当前条目、位置与故障
  (`RemoteStateDto`)—— 不是一份全组标量。计划说放第 6 版的条目 X,而某台手上的执行副本
  还是第 5 版,那台就照第二节「取全了再原子换上」去取;取不到、条目不在、媒体取不到或
  跳不到位置,它报故障、不出声,不自己从头放、不换下一首,也不把别的成员拖回它的位置。

跟着变的几处:

- **完整执行副本与失败原子性不变。** 加入组的成员照样按标识取整份副本,准备不了就不进组
  (`CommitOutputs` 只提交跟上的子集);本轮不批准「先执行半份队列」。
- **排列属于执行状态,随计划交接**(第六节的延伸):主端交接时新主端照上一任的播放次序与
  循环模式接着放,不按自己的开关另起一套。次序只在变了的时候随计划下发(整份几千条,每秒
  心跳都带就是白白几十 KiB),超过三千条不下发(一条信令 64 KiB 的上限),交接后新主端按
  自己的次序往下放。
- **单机本地先行起播与异步持久化不变**(第八节):登记组、固定队列这些网络门槛只加在组
  操作上;组外的本机播放一个字节不变。
- **自动下一首的红线不变**(第四节):主端自己推进下一首,不等服务端批准;跟随端不自己推进,
  照计划预告的下一首到点换过去。

## 要跟着改的文档

本篇只定架构。下面几处的改写在 `#109` 的文档那一项里落地:

- `0030` **第二节「队列归被控端」整节改写**:队列定义由服务端持久保存;播放端
  持有已应用版本的完整执行副本,负责实际播放与自动推进;遥控器从服务端读取
  队列,并以播放端的报告确认当前应用版本与实际位置。
- `0030` **第三节「服务端只转发」**:对 `Signal{to, payload}` 仍成立,对队列
  不成立 —— 服务端现在解释并持有队列。
- `0030` **第四节「服务端不缓存状态」**:改为服务端持久保存队列定义与最近一次
  执行报告,但**不假装它是实时的**;`SnapshotRequest` 仍向被控端要当下状态。
- `0030` 第一节里那份每秒上报的字段表跟着换成小状态。
- `0018`:三条缓存规矩一条不改,补一段说明队列条目不是缓存 —— 它删了会丢
  用户数据,所以不归那三条管,也不外键指向 `platform_tracks`。
- `CONTEXT.md`「队列」词条:从「音乐页最近一次装进列表的东西」改成有身份、
  有版本、活得比任何一台客户端久的实体;「被控端」词条跟上三层裁决的说法。
