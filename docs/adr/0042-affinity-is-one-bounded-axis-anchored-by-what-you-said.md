# 喜爱度是一条有界的轴,锚在用户说过的话上

日期:2026-11-12。状态:已采纳。扩展 #157 的赞踩;红心(`0033`)不变。

## 背景

#157 的赞踩是两态加「未表态」,`track_feedback.verdict ∈ {1, -1}`。它答得出「这首赞过没有」,
答不出「这几百首红心里我最爱哪些」:红心是收藏,赞是「不错」,两者都是一刀切的布尔值。
播放事件(`play_events`,#157 起带 `listened_ms`/`duration_ms`)里其实有更细的信号 ——
哪首每次都听完、哪首总在前奏切走 —— 但没有地方把它与用户自己的表态放到同一把尺子上。

用户要的是:能按「有多喜欢」给「我的喜欢」和本地歌单排序、分档筛选,心动模式从最爱的歌
出发,而**不必**给每首歌手打一个分。

## 决策

一条轴,叫**喜爱度**,值域 `[-1, 1]`,线上 ×1000 存成 `-1000..=1000` 的整数
(`TrackFacetsDto.score`,`i16`)。由两层叠成,算在服务端一处(`server::score`):

```
score = clamp(锚 + 修正, -1, 1)
```

### 锚:用户写

`track_feedback.verdict` 放宽成 `{-1, 1, 2}`(迁移 `0030_track_feedback_loved.sql`),
未表态仍是「没有这一行」:

| 档 | verdict | 锚 |
|---|---|---|
| 踩 | -1 | -0.6 |
| 未表态 | 无行 | 0 |
| 赞 | 1 | +0.4 |
| 特别喜欢 | 2 | +0.8 |

抽屉里「点赞」旁边多一块「特别喜欢」,点法与赞踩相同:点亮着的那块取消,点另一块换成那一档。

### 修正:播放写

每一次记下了听多久、时长已知的播放给一个值 `v ∈ [-1, 1]`:

- 听不到 3 秒(`NOISE_MS`)的不算信号 —— 连按「下一首」找歌时路过的那几首什么都没说明。
- 完播率 `c = min(听了多久 / 时长, 1)`;`c ≤ 0.1` 为 -1,`c ≥ 0.9` 为 +1(片尾常有尾奏),
  中间线性:`v = clamp(2·(c − 0.1)/0.8 − 1, −1, 1)`。

按 90 天半衰期衰减后求和,`S = Σ v · 0.5^(天数/90)`,再压进界里:

```
修正 = 0.2 · tanh(S / 3)
```

取整到 ×1000 之后再收进 `±199`。尺度 3 的意思是:净完播(衰减后)三次,修正走到界的
`tanh(1) ≈ 76%`,一次听完约 +0.064。

### 分档

客户端的「喜爱度」筛选与分组分四档(`app_core::facets`,服务端 `radio::filter` 照抄一份,
对拍测试钉住):

| 档 | ×1000 |
|---|---|
| 特别喜欢 | ≥ 600 |
| 喜欢 | 200..599 |
| 一般 | -199..199 |
| 不喜欢 | ≤ -200 |

锚的档距(0.4、0.4、0.6)至少是修正界的两倍,修正又收在开区间里,所以每一档**恰好**是一个锚
加减修正:分档读出来就是用户说过的那句话,修正只在档内排先后。

### 用在哪

- 「我的喜欢」与本地歌单的列表接口带 `?sort=added|score|plays`(`TrackSortDto`),服务端在
  填完聚合之后稳定排序,同分保持加入时间的次序(`0021`:展示次序由后端定)。不带就是加入时间,
  老客户端不受影响。界面在筛选条最前面摆一颗「排序」选择 chip。
- 电台补歌接心动模式时,种子先从喜爱度最高的 20 首(红心与赞过、特别喜欢过的里挑,喜爱度为正)
  里轮着取,不够再用最近听过的。赞踩过的歌照旧不进电台,特别喜欢同样算表过态。

## 为什么有界

无界的累加分(播放次数、听歌时长)会让听得久的歌永远压着新歌,单曲循环一晚就能把一首歌
推到用户亲口说过「特别喜欢」的那首之上。行为是**佐证**,不是陈述:它该修正位置,不该推翻
用户说过的话。界取 0.2、锚距取 0.4,是为了这条性质能从数字上直接看出来,而不是靠调参碰巧成立。
`tanh` 让第一批播放有分量、后面的递减,一首歌被听了一百遍和三十遍差不多 —— 那本来也说明不了更多。

衰减是因为口味会变:一季之前天天跳的歌,今天未必还跳。

## 为什么红心不并进来

红心回答的是「留不留」:它决定「我的喜欢」的成员、预取、永久保存(`0033`、`0037`)。喜爱度
回答的是「有多喜欢」。两件事会分开变:收藏了但最近听腻了,没收藏但每次都听完。把红心折成
锚的一档,就得在「取消红心」时同时改评价,或在「踩」时同时删收藏 —— 两个独立的意图被绑成一个。
所以红心不变,与喜爱度正交;「我的喜欢」里照样能按喜爱度排。

## 备选方案

**让用户手打分(1–5 星或 0–100)。** 不选:打分是持续的劳动,千首红心没人会打完,打了的
那部分也会因为「当时心情」而互相不可比。四档里有三档是一次点击就有的态度,其余交给播放行为。

**只用播放行为,不要锚。** 不选:行为噪声大(在别的房间放着、睡着了),而且说不出「不喜欢」
与「没听过」的区别。用户愿意说的那句话比一百次播放更可信。

**在 SQL 里算。** 不选:公式要单测、要有一处真相。SQL 只把每首的播放按列聚成数组
(`store::facets::LISTENS`),公式在 Rust 里,千首的歌单仍是一条查询。

**修正能跨档。** 不选:那样一首赞过的歌被跳几次就会掉进「一般」,筛选「喜欢」时它消失,
用户会以为赞没存上。

## 代价

- 还在放的那一次此刻只有检查点的累计,算出来像没听完;放完补记后自己改正。进程被杀的那一次
  停在最后一个检查点,永远读成没听完 —— 接受,它只占一次播放的分量。
- 喜爱度每次读列表时现算,不存。千首的歌单要多拉每首的播放数组,`server/tests/facets.rs`
  的千首用例守着耗时。
- 筛选维度的线上名从 `verdict` 改成 `score`(`serde(alias)` 仍认旧名)。老客户端带着「赞」
  「踩」这类旧 chip 文字去续电台的话,那一维筛不出歌;客户端与服务端随同一次发版上线,
  不另做翻译。`PROTOCOL_VERSION` 不动:新字段带默认值,旧字段语义只扩不改。
- 抽屉的动作磁贴从五块变六块,手机上一块约 47px,「特别喜欢」四个字刚好放下;再加一块就得
  另想排法。
