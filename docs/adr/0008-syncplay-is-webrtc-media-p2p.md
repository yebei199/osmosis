# 同播走 WebRTC 媒体轨,P2P 星型,服务端只做信令

日期:2026-07-27。状态:已采纳。

## 背景

本项目要做同播(见 `CONTEXT.md`):用户的多台设备(android + linux 先行)同时播放
同一首歌。歌曲来自 bang-dream 聚合层,每台设备本可以各自向 axum 要一份播放地址。

先把动机说诚实:**WebRTC 是这次的学习目标,不是从需求推导出来的最优解。**
本仓库是 study 仓库,练到真实的 ICE/SDP/RTP/媒体栈本身就是需求的一部分。
下面的备选方案分析回答的不是「哪个最省」,而是「选了 WebRTC 之后,哪种用法最值」。

## 决策

- **媒体轨,不是 DataChannel。** 主控把解码后的音频经 Opus 重编码,以 audio track
  推给每个听众。听众播的是主控送来的流,不是自己拉的直链。
- **P2P 星型。** 主控与每个听众各建一对 PeerConnection,声音不经过服务器。
  自家设备大概率同一局域网,ICE 直连成功率极高,3–5 台设备的上行带宽扫得起。
- **axum 只做信令。** WebSocket 转发 SDP/ICE,不碰媒体字节。信令消息的形状进
  `contract` crate —— 它们是客户端与服务端之间的线上格式。
- **技术栈:** 客户端用 `webrtc` crate(webrtc-rs,Pion 移植)。音频管线第一段就用
  rodio 建,它的 `Source` 是采样迭代器,第二段在中间 tee 出 PCM 喂 Opus 编码器,
  不必推倒重来。

## 备选方案

**各自拉直链 + 时钟对齐。** 每台设备自己找 axum 要播放地址,网上只跑「放哪首、
从第几毫秒、何时开始」的控制消息。带宽近零、无重编码、每台设备拿自己能放的最高音质。
代价是要自建时钟同步,对齐精度受制于它。**不选**:它绕开了媒体栈 —— 而媒体栈正是
这次要学的东西。若某天目标从「学」变成「用」,这个方案值得重新翻出来。

**axum 当 SFU。** 每台设备只与服务端建一条连接,声音由服务端分发。主控上行只需一份,
断线不塌全场。**不选**:服务端要引入整套 webrtc 栈,复杂度翻倍,声音多一跳;
单人自用场景里星型的弱点(主控上行 ×N)根本压不到。

**DataChannel 只传控制。** 是「各自拉直链」的 WebRTC 皮版本,同样绕开媒体栈,同样不选。

## 代价

- 主控设备承担解码 + N 路 Opus 编码 + N 份上行。手机当主控时是真实的电量与带宽负担。
- 听众收到的音质由主控的重编码决定,上限低于各自拉直链能拿到的档位。
- 会话生死系于主控:主控断线即会话终结,听众各自停声(规则定义见 `CONTEXT.md`
  「同播会话」)。不做暂停等待,不做听众接任 —— 单人场景里重新发起就是点一下的事。
- 播放控制单向:只有主控能控,听众只调本地音量。省掉指令转发、幂等、回声抑制一整层。
- wasm 端将来接入时要换一套实现(浏览器内置 RTCPeerConnection),webrtc-rs 不能编译
  到 wasm。这条分歧会被吸收在 `api` crate 的 platform 模块里,与 `docs/adr/0002`
  同一个模式。
