# 版式由运行时窗口宽度决定,不由「端」决定

日期:2026-07-13。状态:已采纳。

## 背景

界面原本只有一种排布:左侧 96px 竖导航栏 + 右侧内容区,六个端共用一份。手机上这套排布是坏的:

- 96px 的竖栏吃掉手机竖屏(~393dp)四分之一的宽度;
- Home / Server 的玻璃卡片写死 340px 宽,比剩下的内容区还宽 —— 内容区在导航栏之后绘制,
  卡片于是**盖住了导航按钮**;
- 3D 热调工具条里「220px 按钮 + 4×72px 参数框」= 576px 的固定内容,塞进 265px 的玻璃卡,
  后面几个参数框被 `clip` 静默裁掉。

要修,就必须让排布随可用空间改变。问题是:**依据什么切换?**

## 决策

在 `.slint` 里按**运行时窗口宽度**判断:

```slint
property <bool> compact: root.width < 600px;
```

窄 → 底部导航栏;宽 → 左侧竖栏。Rust 侧完全不参与,不存在任何 `cfg!(target_os)` 分支。

同时在 `CONTEXT.md` 里把**版式 (Layout Mode)** 立为一个独立术语,与**端 (Platform)** 正交。

## 备选方案:编译期按端判断

`cfg!(target_os = "android")` 推一个 `is-mobile` property 进 UI。语义上更贴近既有的「端」,
`CONTEXT.md` 里现成的词汇就够用,不必新造术语。

不选它,三个理由:

1. **判断依据本身是错的。** 「端」定义为**运行时能力与打包形态**(有没有文件系统、怎么装),
   而排布要回答的是「此刻有多少横向空间」。这两件事在平板、折叠屏、桌面窄窗、手机横屏上
   **全部对不上**:安卓平板横屏有 1280dp 宽,按端判断它会得到一个为 393dp 设计的底部导航。
2. **移动端排布在桌面上永远看不见。** 这是最致命的一条。按端判断,唯一能看到紧凑版式的
   办法是构建 APK、装机、截图 —— 一个改动一次几分钟。按宽度判断,桌面上把窗口拖窄就是
   紧凑版式,`just shot 420` 一条命令拿到真实像素。**能被廉价验证的东西才会被真正验证。**
3. **它省不下什么。** 一个 `root.width < 600px` 的表达式并不比一个注入的 property 更复杂,
   反而少了一条 Rust → UI 的推送链路。

## 代价

- 版式会随窗口尺寸**跳变**。桌面用户把窗口拖过 600px 时导航栏会从左边跳到底部。这是
  Web 端习以为常的行为,但对桌面原生应用来说略显意外。接受它 —— 换来的是移动端排布的
  可验证性。
- 断点值(600px)是个**魔数**。取自 Material 的标准断点:手机竖屏(~393dp)落在紧凑侧,
  手机横屏(~850dp)回到宽版式 —— 横屏本来就矮,底栏再吃 64px 太亏。
- 3D 页的相机因此也必须跟着视口长宽比走(竖视口要后撤,否则横向排开的形状出画),
  见 `crates/render3d` 的 `pullback`。这是版式决策外溢到渲染层的唯一一处。
