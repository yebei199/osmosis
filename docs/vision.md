# 架构愿景:Slint + Bevy + 同一个 wgpu 能长成什么

这是一份活文档,记录这套技术选型的能力上限推演。既然选了自带渲染器的路线,
就没有理由只做一个常规的多端 UI 应用:那样的话 Tauri 更省心。这份文档回答的问题是,
这条更贵的路买到了什么别人买不到的东西,以及顺着它能长出什么产品形态。
每轮新的推演直接追加,文末留了更新记录。

## 地基:三端同一个 wgpu Device

物理事实只有一句话:desktop(Vulkan)、Android(Vulkan/GLES)、Web(WebGPU)上,
Slint 和 Bevy 最终跑在同一个 wgpu device、同一个 queue、同一个 swapchain 上。
其余一切能力都是这句话的推论,分三层。

**纹理是共享的。** Bevy 把场景渲进一张 `wgpu::Texture`,Slint 把它当 `Image` 用,
中间没有 readback、没有跨进程句柄、没有格式转换,就是同一块显存换个 view。
反方向同样成立:Slint 渲染一个 UI 子树到纹理,Bevy 把它贴到场景里任何一个 mesh 上。
双向、每帧、零拷贝。

**帧调度是同一个 vsync。** UI 动画和 3D 动画在同一帧提交。标签钉在 3D 物体头顶时,
webview 方案里那个标签永远慢半拍到一拍(位置从 GPU 世界算出、跨 IPC 桥、再等 DOM 重排),
这里是同帧内像素级锁定。

**状态在同一个类型系统里。** Slint 的 property、Bevy 的 Component、`app-core` 的领域
状态全是 Rust 结构体。一个 `SensorReading` 从网络进来,同一帧内既驱动 Slint 的数字
面板又驱动 Bevy 的粒子颜色,不经过任何序列化。Tauri 的每次 UI 与逻辑通信是一次 serde,
这里是一次 borrow。

对比一下别的方案在 UI 与 3D 之间隔着什么:

| 方案 | UI 与 3D 之间隔着什么 |
|------|----------------------|
| Tauri / Electron | 进程边界 + JSON IPC,3D 活在 JS 堆里 |
| Flutter + 原生 3D | Platform View 合成,Android 上要走 SurfaceTexture 外部纹理 |
| Unity 嵌入原生 App | UaaL 整个引擎是黑盒 View,通信靠消息桥 |
| Qt + 自绘 3D | QQuickFramebufferObject,可行但被锁死在 Qt 的调度里 |
| 本方案 | 什么都不隔:一个进程、一块显存、一条类型系统 |

## 只有这套架构能做的合成效果

这些效果的共同点:都要求 UI 系统和渲染器交出各自的中间产物(深度缓冲、法线、光照)
给对方。两个各自封装的系统在接口层面交不出来,这与优化无关,是能力不存在。

**深度正确的 UI。** 场景里的物体可以挡住 Slint 面板的一半:机器模型的剖面标注卡片,
一半在机壳前,一半被机壳挡住,还带景深虚化。DOM 永远只能整层贴在 canvas 上面,
做不出这个。

**真实折射的玻璃 UI。** CSS `backdrop-filter` 是高斯模糊的近似。这里 Slint 面板可以
作为场景中的折射体,背后的 3D 场景经法线贴图扭曲透过来,面板拖动时折射实时变化。
第三方框架里没有能做这件事的,因为没有一个同时拥有 UI 和它背后的场景。

**UI 参与光照。** 亮橙色的告警弹窗弹出时,它的光打在场景物体上,投出橙色泛光。
告警此时已经超出弹窗的范畴,是整个场景被告警照亮。对数字孪生类产品这是一种
别处见不到的视觉语言。

**世界空间 UI 保留完整交互。** Slint 子树渲到纹理、贴在场景里的屏幕或控制台表面,
再把点击射线反投影回 UI 坐标:贴在 3D 物体表面的界面依然可以点、可以滚动、可以输入
文字。Unity 的世界空间 UI 能做类似的事,但 UI 质量停在 Unity 水平;webview 方案出局。

**导航即相机运动。** 页面切换可以做成 3D 相机飞越:从计数器页飞进 3D 页,UI 元素
在飞行中保持锚定各自的世界位置。应用导航和场景导航合并成同一件事。

## 完整的 Bevy 游戏是成立的,而且墙没了

真正独特的地方在于游戏和应用之间没有边界,三个形态:

**游戏是应用的一个页面。** 现有 tab 结构里,3D 页可以就是完整的 Bevy game loop:
ECS、物理、音频、粒子全开。切走时 schedule 降频或暂停,world 还在,状态不丢;
切回来无缝继续。Unity 嵌入方案里"暂停引擎"是一场仪式,这里只是不调
`world.run_schedule()`。

**应用是游戏的真外壳。** 反过来,一个正经游戏的设置、背包、商店、聊天用 Slint 写成
保留模式 UI:有无障碍、有输入法、有文本选择、有 DPI 缩放。游戏引擎阵营在这里烂了
二十年,大厂宁可付席位费嵌浏览器(Coherent Gameface)做游戏内 UI。给游戏配一个
桌面应用水准的 UI,别人用钱买,这套架构里免费。

**三端逐像素一致。** 渲染器是自带的,一个特效在 Linux、真机 Android、浏览器里是
同一份 WGSL。QA 验一端的渲染正确性即可。Tauri 的跨端是"三个浏览器内核上大致一致",
这里是"同一个渲染器编译三次"。wasm 和 femtovg 上踩的坑,换来的就是这个。

性能上限:Bevy 本身面向正经游戏(ECS 并行调度、自动 batching),wgpu 是 Firefox 的
生产渲染后端,Slint 那层每帧的开销约等于多画几十个 quad。也就是说 3D 性能上限等于
Bevy 的上限,UI 不构成税。

## ECS 作为应用数据模型

只把 Bevy 当渲染器用浪费了一半。ECS 是带变更检测、并行调度、查询索引的内存数据库,
`app-core` 的演化方向可以是:

服务端推来十万个实体的状态流,`contract` 反序列化直接落进 Component。同一份数据,
Bevy 的渲染系统查询它画 3D,另一个系统聚合它喂 Slint 的表格 model。前端生态整个
state management 领域解决的"为 UI 复制一份状态树"问题在这里不存在。

变更检测免费:`Query<&Reading, Changed<Reading>>` 只处理这帧变了的实体,
细粒度 UI 更新在数据层就发生了,不需要 signal 或虚拟 DOM diff。

world 可序列化,于是有时间旅行:录下每帧快照,拖一个 Slint 滑块回放整个应用状态。
回放的对象是整个应用而非仅仅 3D 场景,因为应用状态就住在 world 里。

## 继续发散:第二轮推演

**GPU compute 与 UI 同管线。** 同一个 device 意味着 compute shader 的产物直接进
渲染,不过 CPU。百万点散点图在 GPU 上做布局和聚合,GPU picking 算出鼠标下是哪个点,
结果回给 Slint 弹 tooltip。数据可视化领域 web 方案在十万点级别就开始跪,
这里的上限是显卡。

**确定性回放与三端像素级 CI。** `just shot` 已经在截真实像素。往前一步:ECS 快照 +
固定随机种子 = 确定性重放,任何 bug 都能录像;CI 在三端跑同一场景截图做像素 diff,
渲染回归自动被抓住。自带渲染器的方案才谈得上这件事,webview 的像素归浏览器管。

**多人与协同是顺手的。** `server/` 已有 axum,`contract` 已经统一线上格式。ECS 组件
本身就是可同步的最小单元,把 Component 的变更流接上 WebSocket,应用天然长成多人的:
协同 3D 白板、多人看同一个数字孪生、给模拟经营加联机。别的架构里"加多人"是重写,
这里是给已有的变更检测接一根管子。

**应用本身是编辑器。** Slint 有 live-preview,Bevy 有 asset 热重载,两者都在进程里。
合起来:应用可以内嵌自己的创作模式,改 UI、换模型、调材质即时生效,不重启。
发布版关掉这个模式即可。工具和产品之间的边界也是可选的。

**空间音频与 UI 联动。** Bevy 的音频系统在同一个 world 里,UI 事件可以有空间化的
声音反馈:告警弹窗的提示音从它锚定的 3D 设备方向传来。桌面应用从来没有过
方向感的音频,因为桌面应用从来没有场景。

**生成式主题:主题即场景。** 应用背景可以是一个完整的 shader 场景(流体、粒子场、
日夜循环),UI 浮在其上并与之互动(前文的折射与光照)。换主题就是换场景。
这条路线的终点是应用的"皮肤"成为可编程、可交互的内容本身。

**XR 是延长线而非转向。** wgpu 加 OpenXR 的路线社区已在铺,Bevy 有 XR 分支。
到那一天,世界空间 UI、深度正确遮挡、空间音频在这套架构里全是已经解决的问题,
迁移成本是接一个新的 swapchain。webview 方案到了 XR 门口要推倒重来。

**WASM 插件沙箱。** 宿主是 Rust,插件可以是 WASM component:用户脚本在沙箱里跑,
通过受控接口读写 ECS。应用长成平台,而安全边界是 wasmtime 级别的,
不是 JS eval 级别的。

**体积与内存。** 单二进制,无捆绑浏览器。Electron 起步两百兆内存,这里的基线是
Rust 应用的基线。嵌入式方向 Slint 本来就能下到 MCU,这套分层(`app-core` 不依赖
slint 和 IO)保留了往下裁剪的可能。

## 有不公平优势的产品原型

**数字孪生 / 工业监控。** 高频传感器流吃零序列化通路,3D 设备模型吃深度正确标注,
桌面级表格与快捷键吃 Slint,现场平板吃 Android 端,演示吃浏览器端。现在这个市场的
玩家是 Unity 工业版(贵,UI 差)和 web 三件套(数据量大就跪),这套架构像为它定制。

**重 UI 游戏。** Football Manager、RimWorld 谱系的游戏苦 UI 久矣。Slint 做游戏 UI,
Bevy 做场景,一份代码出 Steam、Android 和网页 demo。

**创作工具 / 编辑器。** 视口是 Bevy,检视面板是 Slint,所有编辑器都痛的
"视口与面板同步"因为共享 ECS 而消失。节点编辑器、关卡编辑器、素材预览器都在射程内。

**教育模拟。** 物理沙箱、电路模拟、化学反应可视化:模拟跑在 ECS,控制面板是 Slint,
三端同一份代码覆盖教室的桌面、学生的平板和家里的浏览器。

## "UI 一流"的准确含义:上限与斜率

这四个字要拆成两个量,否则就是过度承诺。上限指像素层面最终能画出什么,
斜率指做出一个效果要付多少工程成本。

上限没有封顶。整条 wgpu 管线在自己手里,GPU 能渲染的这个应用就能渲染。
Flutter、web、SwiftUI 都被各自的合成器封顶:web 的 `backdrop-filter` 只有固定几种
滤镜,Flutter 的自定义 shader 拿不到真实场景深度。这里不存在那道顶。

斜率分三个梯队。梯队一是 Slint 原生词汇表:属性动画、easing、states/transitions、
opacity/clip/旋转、渐变、阴影,产品级动效在这层,写几行就有,编译到 native,60fps 稳。
梯队二超出 Slint 词汇表但被本架构解锁:玻璃折射、流动、粒子、任意后处理。Slint 没有
给元素挂自定义 shader 的机制,但 UI 子树可以渲到纹理再用自写 WGSL 合成,现有的玻璃页
就是这层的实践。能做,代价是每个效果都是一次管线工程,没有现成库可 import。
梯队三是生态缺口:Rive/Lottie 式的设计师动效管线、手势弹簧物理、现成组件库,
Slint 生态里基本没有,用梯队二的办法都能造,但对手那边是设计师导出即播放。

一句话:只要能做,这个应用就能做出来,这句成立;做什么都便宜,这句不成立。
对手的成本曲线是缓坡但封顶,这里是陡坡但不封顶。梯队一之外的每个效果都在付
工程成本,换来的是没有任何效果在原理上不可达。文档其余部分说的"UI 一流"
以对比游戏引擎 UI 为语境(无障碍、输入法、文本编辑、DPI),那个对比不受此节限定。

## 扬长避短的打法

主战场选在 UI 与 3D 深度融合的地带,那里以上每条优势都在叠加,而对手连入场资格
都没有。不去和 Unreal 拼画质天花板:拼的是"画质够用 + UI 一流 + 三端一份代码",
这个组合当前没有第二个玩家。数据密集、交互密集、多端分发的场景权重越高,
这套架构的相对优势越大,选题时按这三个维度打分即可。

## 已插下的旗子:深度正确的 UI

2026-07-21 立住了。3D 页正中那张 Slint 注释卡片被转盘近侧的物体逐像素挡住,同一帧里
远侧的立方体则透过玻璃在它背后 —— 一前一后同时成立,切口是物体的真实轮廓而非矩形。

做法不是把 UI 渲进纹理(Slint 没有那个 API),而是把合成拆成三层:场景 → 卡片 → 遮挡层。
遮挡层由第二台相机画,它的深度缓冲预先清到卡片所在的深度,于是只剩比卡片更近的片元,
其余透明;Slint 只做寻常的 alpha 合成。没写一行 WGSL,没动 slint fork,代价是几何提交
两遍。实现与取舍见 [`crates/render3d/README.md`](../crates/render3d/README.md)。

这条立住之后,前文「合成效果」一节里其余几条不再是推演:它们都是同一条管线上的延伸,
区别只在还没做。

## 下一面旗子

**世界空间锚定**:让卡片跟着场景里的某个物体走,而不是钉在画面正中。遮挡已经是逐片元的,
这一步只多一次 `world_to_viewport` 与两个回传属性 —— 做完就是「3D 物体的标注卡片」这个
完整形态,数字孪生那条产品线的第一块砖。

  30,不是本项目能单方面决定的,所以是路线图上的伏笔而非当期动作。
