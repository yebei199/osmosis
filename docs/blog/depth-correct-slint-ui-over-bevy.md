桌面应用里嵌 3D 场景,常见做法是引擎渲进一张纹理,UI 框架把它当图片贴上去。这条路有个躲不开的后果:**UI 永远在 3D 之上**。想让场景里的物体挡住半张面板 —— 比如设备模型的剖面标注卡片,一半在机壳前、一半被机壳挡住 —— 在这种结构下做不出来。

不是难,是不存在。合成器只看到"一张图 + 一些控件",它手里没有深度可比。

我在一个 Slint + Bevy 共享同一个 wgpu device 的项目里把这件事做出来了,没有写 shader,也没有改 Slint 的源码。下面是做法,以及一个远比技术本身花时间的教训。

## 为什么"把 UI 渲进纹理"不是答案

直觉方案是反过来:让 UI 也渲进一张纹理,当作贴图放进 3D 场景,交给深度缓冲处理。世界空间 UI 就是这么做的。

但 Slint 没有"把子树渲染到我给的纹理上"这个 API。它的渲染器绑在窗口上,而一个进程只能有一个 platform,没法再造一个离屏窗口。这条路要么改上游,要么放弃 Slint 自己画 UI —— 那就把选它的理由(无障碍、输入法、文本编辑、DPI 缩放)全丢了。

## 把合成拆成三层

换个角度:UI 不动,让**场景出现两次**。

```
第一层:场景          ← 完整画面
第二层:Slint 卡片    ← 正常的 Slint 控件,有文字、有交互
第三层:遮挡层        ← 只含"比卡片更近"的那部分场景,其余透明
```

Slint 只做寻常的 alpha 合成。它不需要懂深度,UI 也不必先渲进纹理。近处的物体从第三层压下来盖住卡片,远处的物体留在第一层、被卡片盖住。

关键是第三层怎么来。答案是**第二台相机**,与主相机同位、同投影、同色调映射,只差两处:

- 清除色透明 —— 没画到的地方 alpha 为 0,合成时露出下面的卡片;
- **深度缓冲不清到远平面,而是清到卡片所在的深度。**

第二条是全部机关。Bevy 用反向 Z(1 是近平面,0 是远平面),不透明物体的深度测试是 `GreaterEqual`。把深度缓冲预先清到卡片锚点的 NDC 深度,只有比它更近的片元能通过测试 —— 于是这一层天然就只剩"挡得住卡片的东西"。

Bevy 0.19 里就是两个字段:

```rust
Camera3d {
    depth_load_op: Camera3dDepthLoadOp::Clear(anchor_ndc_z),
    ..default()
},
Camera {
    order: 1,
    clear_color: ClearColorConfig::Custom(Color::NONE),
    ..default()
},
```

门槛值不用手推投影矩阵,`Camera::world_to_ndc` 直接给:

```rust
occluder_depth(camera.world_to_ndc(transform, CARD_ANCHOR))
```

它返回的 z 就在深度缓冲的坐标系里。锚点跑到相机背后或投影退化时返回 `None`,这时退回近平面 —— 遮挡层为空、卡片完整可见。**宁可少一个效果,也不能把整幅场景糊在卡片上**;后者是一个刺眼的错画面,前者只是没有效果。wgpu 另外硬性要求清除值落在 [0, 1],越界会被校验层直接拒掉,所以这个兜底同时是防崩溃的。

## 为什么这值得做

因为切口是**逐片元**的。

一个横跨锚点平面的立方体会被那个平面切开,而不是整体跳到卡片前面或后面。CPU 侧按物体距离排序做不到这件事 —— 排序的粒度是物体,物体一穿过平面就会"啪"地翻面。而"UI 整层贴在 canvas 上"的方案在原理上就到不了这里,不管排序做得多细。

这是自带渲染器这条更贵的路线买到的东西之一:UI 系统和渲染器共享同一个 device、同一个 wgpu 类型系统,所以能互相交出中间产物。

## 代价,以及什么时候不该这么做

几何被提交两遍。八到六十来个形状时可以忽略;上千个 drawcall 的场景里就不行了,那时候应该改成"采样深度纹理的一个全屏 pass",代价是要自建渲染图节点和写 WGSL。

另外遮挡层那张图必须**和场景图逐像素对齐**,所以它是整块内容区大小的。在 UI 里要用负偏移把它推回内容区原点,再裁到卡片范围 —— 不裁的话,近处的物体会连工具条一起盖住。工具条是界面外壳,不在场景里,它不该被遮挡。这个区分要自己划,系统不会替你划。

## 真正花时间的部分:我看错了截图

技术部分第一次编译就是对的。然后我看了一眼截图,觉得"卡片还是压在圆环上面",于是开始查管线:

1. 怀疑第二台相机没渲染 → 把清除色改成半透明红。**红色精确覆盖了卡片矩形**,说明相机在渲染、alpha 合成正常、图片定位和裁剪都对。
2. 怀疑深度值 → 把清除值固定成 0.0(远平面),整个场景都画进了遮挡层。机制通的。
3. 怀疑每帧写入深度没传到渲染世界 → 加了个环境变量旋钮,一次编译多次取样,二分门槛。

第三轮的数据说话了:远处那个立方体在门槛 0.008 和 0.011 之间消失,而它按 `near / 距离` 算出来的深度是 0.00854。**手算和 GPU 完全对得上,管线从第一帧起就是正确的。**

那近处的圆环为什么"没挡住卡片"?因为它挡住了 —— 只是压到卡片下缘一小条,而我看的是一张缩放过的截图,在那里"物体盖住卡片"和"半透明玻璃透出那个物体"长得一模一样。

真正的判据是**卡片那 1px 的边框在不在**:

```
y=1055  x=851: (66,66,68)   ← 边框亮线,卡片在上
y=1070  x=851: (116,154,209) ← 与左右两侧同色,边框没了,物体在上
```

再加一条:卡片下沿处像素**没有台阶**。如果卡片压在圆环上,跨出卡片边界会丢掉 12% 的白色叠加和那道边框,必然出现跳变。实测是平滑过渡的。

## 可复用的结论

**判据要选二值的、能一个像素定胜负的东西。** "看起来谁更亮""好像有点被挡住"不是判据,那是观感。边框在不在、跨边界有没有台阶,才是。

**看不出效果时,先确认取景,再怀疑管线。** 我跳过了"近处物体到底有没有落进那块矩形"这个问题,直接去查相机、alpha 和深度,白花三轮。取景是最便宜的检查,应该排在最前面。

**可复现不等于真实。** 这条我在同一个项目里栽过第二次了。上一次是据一张缩放图断言存在"底部残影",还写进了 commit 消息,后来读真实 PNG 才发现那块区域是纯背景色 —— 中间我甚至做过一次"对照实验",但对照组和实验组是在同一个被污染的呈现管线里看的,于是假象一致地出现在两边。

两次的方向相反:一次把不存在的缺陷当成真的,一次把已经生效的效果当成没生效。根因是同一个 —— 用呈现给我的图像下像素级结论。
