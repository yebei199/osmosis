# 可视化表面:深度 UI 的正确落点,以及音频这个载荷

`vision.md` 论证了这套架构**能**做什么。这份论证的是**该往哪落** —— 因为同一个能力用在
不同表面上,收益是反号的。结论:通用 UI 是负收益,可视化表面是正收益,而音乐可视化是
验证整条链路最合适的第一个载荷。

## 一、为什么 2D 屏幕上没人这样做 UI

先纠正问法。这种 UI 是存在的,只是不在这块屏幕上:XR 里它是标配 —— Vision Pro 的窗口
有厚度、有投影、被真实物体遮挡;VR 菜单是浮在空间里的板子;Unity 的 `World Space Canvas`
是十几年的标准组件。**空白的是桌面与手机的 2D 屏幕,问题应该是它为什么没下沉。**

### 技术层面:能做 UI 的做不了深度,能做深度的不想做 UI

| 栈 | 障碍 |
|----|------|
| Web | DOM 与 canvas 是两套合成体系。CSS 3D transform 有透视没有深度缓冲,DOM 元素不可能被 canvas 内的物体逐像素遮挡 |
| iOS / Android 原生 | view 层级是 2D 合成树,SceneKit / SceneView 是嵌进去的一块**矩形**,UI 与 3D 互不知情 |
| Flutter | Impeller 自渲染 UI,最接近,但渲染模型仍是 2D 图层树;外部 3D 纹理接进来还是矩形 widget |
| Unity / Unreal | **能做**,但其 UI 系统写业务界面是酷刑,没人拿它做设置页 |

本项目站在唯一的交叉点:一个自带渲染器的 UI 框架与一个 3D 引擎共用一个 wgpu device。

### 但主因不是技术,是负收益

Unity 能做这件事已经二十年,没人拿它做桌面软件界面 —— 说明是**想到了并且否决了**:

- **UI 的第一职责是可预测。** 会被撞歪的设置面板,第一次是惊喜,第三次是差评。用户来是
  完成任务,不是看界面表演。
- **无障碍一票否决。** 屏幕阅读器读不了在 3D 里飘的东西,焦点顺序与键盘导航失效,动效
  触发前庭失调。任何要过 WCAG 的产品碰都不能碰。
- **投入产出为负。** 要付新设计规范、新交互模式、无障碍改造、多端一致性、QA;换来的是
  没有用户会为此付费。这个提案活不过第一次评审。

炫技产品也不做,是因为**它们炫的是不冒险的部分** —— 材质、光学、动效曲线,提升质感但
不动摇用户的心智模型。打破心智模型不叫炫技,叫冒险,而商业产品的炫技预算不给后者。

还有个朴素障碍:**整条工业流水线上没有一环容纳「UI 有深度」**。Figma 没有深度,设计稿
交付不了,前端不知道怎么实现,QA 不知道怎么验收。本项目能做,是因为把设计、实现、验收
压缩成了一个人,且渲染器归自己。

### 这正是探索项目的特权

约束不同:不用过 WCAG、不用说服产品经理、不用交付设计稿、渲染器自有、目标是观察而非
转化率。**探索项目的特权就是可以做负收益的事** —— 商业产品不会去探的地方,只能由这类
项目去探。「为什么没人做」这个答案本身就是一条观测结果。

## 二、换一个表面,三条否决全部失效

| 否决理由 | 设置页 | 播放页 / 可视化页 |
|----------|--------|-------------------|
| UI 要可预测 | 硬约束 | **不成立** —— 该表面的职责是氛围,不是效率 |
| 无障碍 | 一票否决 | **可豁免** —— 装饰层不承载功能,本就该 `aria-hidden`,前提是功能有等价路径 |
| 投入产出 | 负 | **正** —— 用户会盯着看几分钟,会话时长长 |

所以正确落点是这几类表面:**播放/可视化页、数字孪生与工业 HMI(标注卡片被前方管道挡住
是刚需不是特效)、游戏内 UI、XR**。2D 屏幕上的通用界面是练兵场,不是战场。

## 三、音乐可视化是最合适的第一个载荷

`vision.md` 有一句断言至今仍是推演:

> 一个 `SensorReading` 从网络进来,同一帧内既驱动 Slint 的数字面板又驱动 Bevy 的粒子颜色,
> 不经过任何序列化

**音频频谱是这个断言的理想实例**:高频(每帧更新)、多消费者(数字面板显示 dB、3D 粒子
跟着跳、玻璃折射强度随低频脉动)、对延迟敏感。而且它自带一个人类能直接判断对错的标准 ——
**跟不跟得上鼓点**。假传感器没有这个性质。

**省电门在这里是加分项,不是冲突。** 与动画背景不同,可视化有天然的开关语义:在播放就动,
暂停就停,切走就停。这把现有的门模式(`render-active`、`nav_transition_active`)推进一格 ——
**门从全局的变成按页作用域的**,反而更能证明那套设计是对的。动画背景的问题见
[`animated-background-and-compute.md`](animated-background-and-compute.md)。

## 四、竞争格局:卖点必须收窄

**projectM** 是 Milkdrop 的 C++/OpenGL 重实现(LGPL),跑在 Linux、Windows、macOS、Android
上,被 Kodi、Audacious 当可视化插件用了十几年,能吃标准 Milkdrop 预设。iOS 与 web 的支持
状态**待核实**,web 至少不是主线。

也就是说「跨平台的 Milkdrop」已经有人做完了,前文那句「一份代码、六端、零桥」里的「六端」
被它占掉五个。**卖点因此要收窄到 projectM 结构上拿不到的两条**:

1. **同一份代码里包含 web**
2. **可视化像素与 UI 在同一个合成体系里** —— projectM 输出一块矩形塞进播放器的一个 view,
   它不知道 UI 存在,UI 也不知道它存在;没有深度,不能零拷贝进 UI 层,不能互相遮挡

对外表述别说「效果炫」(别人也有),说「同一个 shader 在 Linux、安卓真机、浏览器里逐像素
一致,音频到像素之间没有任何序列化」。

## 五、素材从哪来

### 不要碰 Milkdrop 预设格式

`.milk` 预设不是 shader 文件,是三样东西的混合体:EEL2 表达式语言写的 per-frame /
per-vertex 方程、波形与形状的声明式定义、Milkdrop 2 之后的 HLSL 像素着色器。butterchurn
(MIT)做的事是把 EEL 编译成 JavaScript、HLSL 转成 GLSL、再复现整个反馈管线 —— **那是个
编译器项目**。在 WGSL 上吃预设等于重写 projectM。

许可上另需注意:butterchurn 代码是 MIT 可正当复用,而预设是社区几十年积累的语料,授权
状态大多非正式,不建议批量搬运。

### Shadertoy → naga → WGSL

naga 有 GLSL 前端,而它已在依赖树里(`naga 29.0.4`):

```sh
naga effect.frag effect.wgsl
```

要手工补的部分是固定的几处,一次搞定后每个 shader 都一样:Shadertoy 的隐式 uniform
(`iTime` / `iResolution` / `iChannel0`)换成本项目的 `Params`;入口
`mainImage(out vec4, in vec2)` 改成 `@fragment fn fs(...) -> @location(0) vec4<f32>`。

**关键一步:照抄 Shadertoy 的音频数据约定** —— 它把音频作为一张 512×2 的纹理传入
(第一行频谱、第二行波形)。把 FFT 结果写成同样布局,Shadertoy 上所有音频响应 shader
的采样代码就不用改,整个素材库直接可用。

naga 的 GLSL 前端不完整,复杂 shader 会转失败。**它到底能扛多少,本身就是一条值得记录的
读数。**

### 反馈 warp 自己写,一百行

Milkdrop 那种「有生命感」的观感,核心机制只有一条:**反馈 + 形变**。把上一帧稍微缩放、
旋转、位移一点再画回去,新图形叠在上面 —— 拖影、隧道、万花筒都是它的变体。

```
new_frame = draw_new_stuff() + warp(prev_frame) * decay
```

设施已经有了:`glass.wgsl` 本就跑在 bevy 的 ping-pong 纹理上,加一次对上一帧的 warp 采样
即可,不需要预设格式、不需要 EEL、不需要 projectM。

## 六、实做要点

**FFT 在 CPU 上做,别上 compute。** 1024~2048 点用 `rustfft` 在 CPU 上是几十微秒级,数据量
太小,来回传 GPU 的开销比计算本身还大。判据与
[`animated-background-and-compute.md`](animated-background-and-compute.md) 一致:没有 scatter
就不是 compute 的活。

**必须做时间平滑,这是核心 know-how。** 原始频谱逐帧抖动剧烈,直接喂 shader 会糊成噪声。
要快起慢落的包络:

```
env = max(raw, env * decay)    // decay ≈ 0.85~0.95
```

这一行是「看起来跟着音乐」和「看起来在抽搐」的分界线。

**web 与 native 的音频源是两套,按 `api` crate 的既有模式吸收。** native 走 `cpal` 拿 PCM,
wasm 里走 Web Audio API 的 `AnalyserNode`,且浏览器的 autoplay policy 要求必须由用户手势
启动音频。差异在这一层吸收、不向上传播 —— 与
[`docs/adr/0002`](../adr/0002-send-boundary-lives-inside-api-crate.md) 是同一个形状。

**顺序**:

1. 先做反馈 warp(约一百行),验证观感与管线,顺带验证 ping-pong 在 web 端是否正常
2. 再从 Shadertoy 转三五个过来,测 naga GLSL 前端的实际覆盖面
3. 预设格式那条永远别碰
