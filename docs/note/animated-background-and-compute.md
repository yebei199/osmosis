# 动画背景与 compute:着色器选型的边界

两个问题的合并结论:**动态背景该怎么画**,以及**什么时候才轮到 compute shader**。
二者是同一道选择题的两面 —— 判据都是「这段计算的输出形状是不是每像素一个值」。

`vision.md` 记的是这套选型能长成什么(推演);这份记的是具体需求落到哪种 shader 上
(实做边界)。

## 一、动画背景用 fragment,不用 compute

### 判据是 scatter,不是「感觉高级」

fragment shader 只能写自己那一个像素:到处读(gather)、写一处。compute shader 能往
任意位置写(scatter),能用 atomic 做规约。

「每个像素根据坐标和时间算出一个颜色」是 gather 的形状,一个 `time` uniform 就完事。
连带状态的动画(生命游戏、反应扩散、网格流体)也不需要 compute —— 两张纹理来回读写
(ping-pong)即可,而 `glass.wgsl` 本来就跑在 bevy 的 ping-pong 纹理上,设施是现成的。

### 像素风的做法是低分辨率渲染,不是后期做旧

顺序要反过来:**先渲进一张低分辨率纹理(320×180 量级),再用 nearest 采样放大到全屏**。

硬边、色块、无插值糊边 —— 像素感的物理来源就是这个,shader 后期模拟出来的总差一层。
同时它把动画背景最大的一笔开销直接抹掉:1920×1080 是 200 万像素,320×180 是 5.7 万,
省掉约 97%。配色再 snap 到一个固定调色板,味道就齐了。

### 真正的代价:它跟本仓库已有的两道省电门直接冲突

这是本条最重要的结论,优先于任何视觉考量。

仓库当前是**不主动重绘**的取向,已经立了两道独立的门(见
[`crates/render3d/README.md`](../../crates/render3d/README.md)):

- 3D 那条的 `render-active`
- 导航选中器那条的 `ui::nav_glass::nav_transition_active` —— 只在切 tab 的转场期间重渲,
  静止时 Slint 复用上一帧纹理

**一个永远在动的背景会把这两道门一起作废** —— 背景每帧重绘,GPU 就没有躺平的时刻,
两道门省下来的电原样吐回去。android 端尤其吃这一刀:持续发热加掉电。

所以「背景一直动」不是一个视觉决定,是一个**推翻既有省电取向**的架构决定。要做就得配
一组新的门,否则不如不做:

- **降帧**。背景不需要 60fps,像素风尤其不需要 —— 12~15fps 反而更对味,同时省四倍。
- **失焦即停**。窗口失焦 / app 切后台必须停,这条没有商量余地。
- 低分辨率渲染(上一节)本身就是主要解药。

### 不做真视频解码

六个端各有一套解码链(桌面 ffmpeg/gstreamer、web 的 `<video>`、android 的 MediaCodec),
跨端成本极高,还要背一个大文件。程序化生成零资源、任意分辨率、六端同一份 WGSL,
是这条路线唯一说得通的做法。

### 接进来几乎不用改结构

`navglass.rs` + `navglass.wgsl` 已经是一个**不经 bevy 的独立全屏 fragment pass**,在共享
device 上自起,画的就是「暗底 + 一层微极光」。像素背景是同一个模式换内容,不是新设施。

`glass.wgsl` 一行都不用动 —— 它做的是「对我背后的任何东西做模糊」,不关心背后是 3D 场景
还是像素动画。

### 待办:玻璃淡染改成自适应(动态背景的前置条件)

`glass.wgsl` 末尾的淡染强度写死为 `mix(col, vec4<f32>(1.0), 0.10)`。背景越暗玻璃越暗,
而玻璃上的文字、边框亮线是 Slint 画的**固定色**。现在背后是 3D 场景,亮度变化慢,只是
小瑕疵;换成持续运动的画面后,对比度会**持续抖动**,那是真缺陷。

方向是纯 fragment,不需要 compute:每个 fragment 已经拿到了自己背后的模糊颜色 `col`,
按它的亮度反向调节淡染,把玻璃亮度往一个目标带收敛 —— 背景暗就多加白,背景亮就少加。

落地前要先解决三件事,顺序不能反:

1. **在哪个色彩空间算亮度。** Rec.709 的 `dot(rgb, vec3(0.2126, 0.7152, 0.0722))` 只在
   **线性**空间才是相对亮度。bevy 那一路出来的是已经过 tonemap 的显示空间值,直接套这个
   系数算出来的不是 WCAG 意义上的亮度。先确认 `src` 纹理的格式与是否 sRGB-view,再决定
   要不要先解 gamma。**这一步没定,后面的阈值全是空调参。**

2. **逐 fragment 自适应会拆掉「一整块玻璃」的错觉。** 每个像素独立调淡染,等于背后亮的
   地方玻璃变透、暗的地方变白,玻璃内部就出现了跟背景同形的明暗块 —— 看上去不再像一块
   均质的材料。**要用区域亮度而非本像素亮度**:采样模糊结果的低 mip,或者复用
   `blur_disc` 已有的 32 次采样直接累计一个亮度均值(后者不额外花采样,更懒)。

3. **淡染要夹在一个区间里。** 上限太高玻璃变成不透的白板,失去「透」;下限到 0 玻璃就
   消失了。`0.06 ~ 0.18` 只是起点,必须实测调。

验证按 [`AGENTS.md`](../../AGENTS.md) 的口径 —— **量像素,别看整幅图的观感**:用
`just shot` 在场景最暗和最亮两种状态各截一张,量玻璃区域内的平均亮度,改动前后的**差值
应该显著收窄**。观感判断在这里没有分辨力,因为要压的正是一个缓慢的漂移。

排在动态背景之前做:动态背景会把这个缺陷从「偶尔」放大到「一直」。

## 二、compute 在本项目的收益边界

同一条判据:**需要 scatter、atomic,或者输出结构不是「每像素一个值」,才轮到 compute。**

### 有收益

**大规模数据可视化的 GPU 布局、聚合与框选。** 这是唯一一个 fragment 根本做不到、且对得上
产品方向(数字孪生、点云、百万点散点图)的用例。输出是「每个数据点一个位置」而非每像素
一个值,分箱聚合要 atomic,框选要规约成一个变长列表 —— 三条都在 compute 的主场。
`vision.md` 第二轮推演已经点到这条,这里补的是它为什么必须是 compute 而其余几条不是。

### 有条件

**粒子场背景。** 门槛在 10 万量级。几千个粒子 CPU 算完全够,bevy 也有现成的;到十万以上
CPU 每帧的位置更新才成为瓶颈。在那之前用 compute 是自找麻烦。

**端侧 AI 推理。** 走 `burn` 的 wgpu 后端(底层 CubeCL)时算子被**生成**成 WGSL,不是手写。
它的价值是观测 —— 推理能不能接管已有的共享 device、几百毫秒的长 dispatch 会不会冲垮 16ms
的渲染节拍、wasm 上的 WebGPU compute 限制卡不卡得住。**这是望远镜价值,不是功能价值**,
记账时别混成「项目需要 AI」。

### 无收益(明确排除)

- **动画背景** —— 见上半篇,gather 形状。
- **模糊优化** —— `blur_disc` 只在玻璃区域内调用,开销与整屏无关,不是瓶颈。优化非瓶颈是纯亏。
- **玻璃区域的对比度规约** —— 想拿「整块玻璃的平均亮度」回 CPU 让 Slint 选文字色,最懒的
  做法是缩采样到 8×8 再 readback,64 个像素,CPU 算平均。compute 不划算。
- **单点 picking** —— 渲一张 id 缓冲、readback 一个像素即可,是 fragment。**框选**才需要
  compute(规约出变长列表)。边界就在这里。

### 一条前置约束:compute 也得按 WebGPU 的下限设计

核心卖点是「三端逐像素一致、一份 WGSL 编译三次」。WebGPU 的 compute 限制(workgroup 尺寸、
storage buffer 上限、没有 timestamp query 因而测不了性能)比 native 严,一旦按 native 上限
写 kernel,web 端就得退回另一套 —— 与 2026-07-24 记的 mesh shader / 光追那笔取舍是同一个
逻辑。取舍口径沿用那条:不碰三端一致的规模红利可用,碰了的要明说这个效果三端不再一致。
