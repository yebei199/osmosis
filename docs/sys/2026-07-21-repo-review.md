# 仓库现状盘点(2026-07-21)

这份是外部视角的一次通读结论,和 `docs/sys/` 下另一份交接文档不同:那份记的是"某项工作
做到哪了",这份记的是"整个仓库现在是什么状态、哪些地方在腐烂"。数字都是当天量的,会过期,
过期了就重量一遍再改这里。

## 一句话

工程素养明显高于产品体量,而这两者的差距正在变成主要问题。

## 立住的三件事

**架构约束是可执行的。** `xtask/src/boundaries.rs` 把四条 ADR 变成 CI 里跑的断言,
`depends_on` 还专门测了 `tokio-util` 不算 `tokio` 的前缀边界。多数项目写完 ADR 就开始漂移,
这里没有。197 行,是仓库里单位价值最高的一段。

**排查是真的。** femtovg 在 wasm 上每个绘制元素约 500µs,3D 页 39 → 134fps,四个 item 提到
上游。过程见 `../wasm/`。

**推翻自己的部分比结论本身更值钱。** 安卓闪黑那一节写了"上一轮四条结论全错",原因是 250 帧
的样本测不出千分之一的事件;然后**决定不修**,理由和 p 值一起留在 `../ready_issue/`。

## 在腐烂的六处

按修起来的性价比排,不是按严重程度。

### 1. master 停在 13 天前,dev 领先 167 个提交

`git rev-list master --count` = 4,最后一次提交 2026-07-08;`master..dev` = 167。默认分支已经
不代表这个项目了。PR 全部并进 dev(至今只有一个,#6)。

要么把 dev 并回 master 让默认分支恢复意义,要么明说 master 已弃用。维持现状的代价是:
任何人 clone 下来看到的是两周前的空壳。

### 2. issue #1–#4 全开着,活早就并了

四条都是"重构为多端 workspace""引入 xtask 与 CI""打通 contract → api → app-core → ui",
仓库里明明白白已经做完。追踪器停止描述现实之后,它就只是噪音。关掉,或者别再开。

### 3. `test/e2e/probes/` 是已完成排查的遗骸

25 个 spec、1761 行。`just web-test` 只跑 `frame-rate.spec.ts`(见 justfile),**这 25 个文件
没有任何命令会跑它们**。它们是 wasm 帧率那次二分的工具,问题已经解决。

留 `gpu-breakdown` 和 `minimal-repro` 这类还能复用的,其余删掉 —— git history 才是归档。
放着不动的代价不是磁盘,是每个新来的人都要判断一次"这些还算数吗"。

### 4. `frame-rate.spec.ts` 是红的,而且写进了交接文档

帧率断言过了,GPU 每帧仍是天花板的 3.9 倍、超出 3 倍上限。**已知红的测试一周内就变成墙纸。**
要么按现实把上限调松并注明为什么,要么 skip 掉留链接。长期红比没有更糟:它训练所有人无视
这一栏。

### 5. render3d 完全没有 CI 覆盖(已部分处理)

它不在 `default-members` 里(理由正当:拖整个 bevy),于是裸 `cargo test` 从不碰它,
`.github/workflows/ci.yml` 也根本不编 bevy。**相机后撤那几个单测从写下来到今天一次没跑过。**

2026-07-21 已把 `cargo test -p render3d` 加进 `just ci`。**仍未决:GitHub workflow 要不要也编
bevy。** 会给每次 run 加几分钟,换来 3D 那条链路在 PR 上有验证。现在的状态是:3D 代码只有
本地 `just ci` 这一道防线,而 dev 分支的 push 本来就不触发 CI。

### 6. 文档与产品的比例倒挂

Rust 2275 行、Slint 450 行,对 Markdown 2248 行 + TypeScript 1772 行。投入最多的产出物是散文。

如果这个项目的产品就是知识(它叫 study),没问题。如果目标是 `docs/vision.md` 里那些形态,
那现在有的是脚手架和仪表盘,东西本身还是一个三页签的应用。

`vision.md` 尤其要警惕:它论证得很好,但在 2026-07-21 之前是一张没有兑现的支票。那天插下的
第一面旗子(深度正确的 UI)把它从零变成一,**接下来该做的是继续兑现,而不是写第三轮推演**。
推演与验证的比例应该反过来。

## 一处需要澄清的许可证问题

LICENSE 是 GPL-3.0 外加一条"OpenAI 及其关联公司不获得任何授权"。GPLv3 §7 下,附加限制是
接收方**可以移除**的 further restriction。当声明可以,但它不是一个能执行的授权条款。要真正
限制使用,得换一个非 GPL 的自定义许可证 —— 代价是失去 GPL 生态的兼容性。

## 一个已被证伪的说法

`vision.md` 曾把 ECS 当作 `app-core` 的演化方向。这与 `boundaries.rs` 正面冲突:依赖链是
`apps/* → ui → app-core`,而边界检查禁止 `app-web` / `app-ios` 的默认树里出现 bevy。
ECS 一旦无条件进 app-core,那条断言当场红。要走这条路,得先决定牺牲哪一个。

2. 关掉 #1–#4,决定 master 的去留;
3. 清掉探针,处理红测试;
4. 决定 GitHub CI 要不要编 bevy。

前两条都是半小时的活,第三条能让仓库的信噪比明显变好。
