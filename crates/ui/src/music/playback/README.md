# playback

放哪一首,以及放的时候条上发生什么:控制条的绑定(`controls`)、一条播放
意图的派发(`dispatch`)、起播与切歌的传输层(`transport`)、自动续播与
下一首的预取(`advance`)。

与 `../list`、`../feed` 的分法:那两个管「摆出哪些歌」,这一组管「放哪一首」。
解码与设备归 `crates/audio`,队列规则归 `app-core`。

## 一条播放意图只有一个入口

用户按下去的那一下分三段走,`dispatch` 是中间那一段,也是唯一定夺的地方:

| 段 | 在哪 | 干什么 |
|---|---|---|
| translate | `controls`、`media` 各自的回调 | 组装整批,翻成一条 `Intent`。不知道这一下会落在哪台设备上 |
| dispatch | `dispatch::dispatch` | 来源检查 → 目标选择 → 本机执行 / 远端提交 |
| execute | `dispatch::execute` | 与来源无关的共享执行体:命令落到本机播放器上 |

**路由按已选目标(`Output`)走,不按提交结果那个布尔值。** 目标在别的设备
而提交失败时声音不回落本机,而是保留目标并说一句「控制暂不可用」
(`docs/adr/0030`)。这一条是 #108 改掉的那一半 —— 从前六个回调各写一遍两道闸,
其中三处发不出去就径直落到本机上。

`execute` **不**只给遥控命令用,所以名字里不带 remote:遥控器发来的命令
(`bind_remote`)、本机用户动作(经 `dispatch` 的本机分支)、自动续播三个
来源共用它。「本机播放也应该当作自己控制自己」指的就是这一层 —— 共用命令
执行语义,但本机不因此建立一个自己遥控自己的会话。

收到的命令**直接**进 `execute`,不经过 `dispatch`:进去的话这台会把收到的
命令再转发回去,而那道被控锁拦的是这台机器前面那个人,不是遥控它的那个人。

## 本机与遥控**不**相同的那几处

统一掉任何一条都会悄悄改变用户看得见的行为,所以逐条钉在测试里
(`../tests/dispatch.rs`):

- 本机播放器已空时按播放是**重播**,不是 `Resume`(`local_toggle`)。遥控那侧
  没有这一档 —— 上报里没有「播放器空没空」这一位。
- 连点去重读的是**本机**的 playback,所以只在本机分支上问。早于目标选择去问的话,
  刚切到遥控时本机残留的 `Loading` 会把用户点的第一首静默吞掉。
- 音量存盘归**设备执行**这一侧:真正改变响度的是哪台机器,记住这个数的就是哪台。
- 音量**不受**被控锁限制,transport 受(#108 实施计划第 6 条的产品裁决)。

跳转是异步的:请求送到解码线程后立刻挂「缓冲中」,落地与失败由每秒那趟轮询
取回(`controls::push_seek_state`)。

## 遥控链路的日志

一次点歌跨三个进程四跳,四跳各有一条 info 级日志(#108 AC-7),文案由
`RemoteCommand::summary` 统一,`grep` 得起来:

1. 遥控器提交 —— `sync::remote::Remote::send`,带成败与原因
2. 客户端入队 —— `syncplay::Client::command`
3. 服务端转发 —— `server::syncplay::control`,带有没有命中槽位
4. 被控端收到 —— `sync::remote::handle` 的 `Event::Command`

**提交成功只说明本地交出去了。** 后面三跳任何一跳都可能悄悄丢掉它,
真放起来了以被控端的上报为准。
